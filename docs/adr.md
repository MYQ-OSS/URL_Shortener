# ADR — 架构决策记录

> 每做一个技术决策就记一条：**当时有哪些选项 / 选了哪个 / 为什么 / 放弃了什么 / 数据依据**。
>
> 这份文档是面试时"这个项目是我自己想的"的**唯一硬证据**——因为它记录了你**放弃过什么**，
> 而照抄开源项目的人没有放弃过任何东西。
>
> 格式：背景 → 考虑过的方案（带对比表）→ 决策 → 放弃了什么 → 数据依据（如有）

## ADR-001 保持 Spring Boot 4.0.7，不降级到 3.5.x

**背景**：脚手架用的是 Spring Boot 4.0.7 + Java 21。Boot 4.0 = Spring Framework 7（2025-11 GA），
生态较新，担心 MyBatis-Plus / Sentinel / MQ starter 跟不上。

**考虑过的方案**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 降级到 Spring Boot 3.5.x | 生态成熟、社区踩坑多、企业在用 | **3.5.x 的 OSS 支持已于 2026-06-30 结束**（末版 3.5.16），等于迁到 EOL 分支 | ❌ |
| 保持 4.0.7 | 支持至 2026-12-31；核心依赖实测已支持 | RocketMQ starter 不支持；ShardingSphere 未声明兼容 | ✅ 采用 |
| 升到 4.1.x | 支持至 2027-07-31 | 更新，踩坑更少人踩过 | ⭕ 可选，但收益不大 |

**逐组件核实结果（2026-07）**

| 组件 | 状态 |
|---|---|
| `mybatis-plus-spring-boot4-starter` | ✅ 自 3.5.13（2025-08）提供；3.5.17 的 POM 直接引入 `spring-boot-dependencies:4.0.1` |
| `redisson-spring-boot-starter` | ✅ Redisson 4.0.0 明确支持 "Spring Boot 4.0 integration"；4.5.0 对齐 Boot 4.0.6 |
| `spring-cloud-alibaba` (Sentinel) | ✅ 2025.1.0.0（2026-02）明确 "Support Spring Boot 4.x" |
| `spring-boot-starter-amqp` | ✅ Spring 官方维护，与 Boot 同步发布 |
| `rocketmq-spring-boot-starter` | ❌ 最新 2.3.6（2026-06 发版）parent POM 仍是 Boot 2.7.18 / Spring 5.3 / Java 8 |
| `shardingsphere-jdbc` 5.5.3 | ⚠️ Starter 已在 5.3.0 移除（官方推荐 JDBC 驱动模式，这点我们方案是对的）；但无 Boot 4 兼容声明，且仍依赖 Jackson 2.x 而 Boot 4 默认 Jackson 3.x |
| `spring-boot-starter-web` | 已改名 `spring-boot-starter-webmvc`，旧坐标作为**废弃别名**继续发布，不会编译失败 |

**决策**：保持 4.0.7。RocketMQ 换成 RabbitMQ；ShardingSphere 在 Day 1 冒烟验证。

**放弃了什么**：放弃了 RocketMQ 的事务消息作为面试素材（改为"我调研过但没选，理由是版本基线对不上"——
这个理由是可核实的事实，比"感觉它太重"有力得多）。

**教训（值得单独讲）**：我原本的判断是"生态跟进慢所以降级保稳"，这是凭印象决策。
**去查了每个组件的真实版本号和发布日期后，结论完全反了。** 技术选型必须查当下状态。

## ADR-002 号段发号器的两个实现坑

**背景**：号段模式（双 Buffer + 乐观锁）看起来简单，实测踩了两个坑，都是压测才暴露的。

### 坑 1：固定小重试上限会被高并发打穿

最初写的是"最多重试 3 次，超过抛异常"。1000 线程压 100 万 ID 时**大量线程直接抛异常**。

原因：一个线程完全可能连续 3 次都撞上"号段刚好被别人耗尽"的时刻，
**重试次数和并发度是正相关的**，固定小上限必然被打穿。

**修法**：循环推进直到成功，只用一个宽松上限（128）兜住"DB 真挂了"的死循环。
每次 `advance` 要么换上一个还有 step 个 ID 的新段（一定能推进），要么因 DB 不可用抛异常。

### 坑 2：★ 预加载与同步取号的竞态会让号段倒序使用

**复现路径**：

```
1. 预加载线程向 DB 申请到号段 [100001, 200000]，还没写进 next
2. current 恰好在此刻耗尽，advance 看到 next == null
3. 于是走同步取号，从 DB 拿到 [200001, 300000] 装进 current
4. 预加载线程这时才把 [100001, 200000] 写进 next
5. 等 current 再耗尽，切到 [100001, 200000] —— ID 倒退了！
```

**后果不是重复**（区间互不相交，唯一性没问题），**而是破坏趋势递增**。
而"趋势递增"正是我们用它做 InnoDB 聚簇索引主键的**全部理由**：
一旦 ID 倒退，插入就变成随机位置写 → 页分裂 → 写放大。
**这个 bug 会静默地把发号器的核心价值抵消掉，而且压测不易发现。**

**修法**：`advance` 里只接受 `prepared.min > stale.max` 的号段，否则丢弃并重新同步取。
因为 DB 侧 `max_id` 单调递增，同步取到的一定大于此前分配过的一切。
丢弃一个号段的代价是浪费 step 个 ID —— 在 568 亿的空间里免费。

**数据依据**（1000 线程 × 1000 = 100 万 ID，模拟 DB RT 200μs）

| step | 耗时 | DB 取号 | 同步取号 | **丢弃倒序号段** | 唯一性+递增 |
|---|---|---|---|---|---|
| 1,000 | 236 ms | 1164 | 823 | **163** | OK |
| 10,000 | 49 ms | 104 | 64 | 3 | OK |
| 100,000 | 44 ms | 11 | 4 | 0 | OK |
| 1,000,000 | 90 ms | 2 | 1 | 0 | OK |

**两个结论**：
1. step=1000 时**实测发生了 163 次 ID 倒退**（已被修正逻辑拦下）——这个 bug 是真的，不是理论担忧
2. step 必须按创建 QPS 来定；本地 buffer 削掉了 **99.999%** 的 DB 访问

**放弃了什么**：`cursor.getAndIncrement()` 会冲过 `max`，超出的那些 ID 被浪费。
这是刻意取舍——**用"浪费几个 ID"换"取号路径完全无锁"**。号码空间免费，加锁不免费。

**其他已知取舍**：服务重启会丢内存里未用完的号段。本场景完全可接受；
但如果是订单号，丢号会导致对账问题。**能区分"哪些业务能容忍丢号"是这个方案的关键判断。**

## ADR-003 短码生成与编码方案

**背景**：需要全局唯一、尽可能短（目标 6 位）、且**不可被顺序枚举**的短码。

**四级方案阶梯**（这个阶梯本身就是最好的面试素材，因为它记录了推理过程）

| 级别 | 方案 | 位数 | 唯一性 | 抗枚举 | 结论 |
|---|---|---|---|---|---|
| — | UUID | 22 | 天然 | 强 | ❌ 太长 |
| — | 雪花算法 | **10-11**（随时间增长） | 天然 | 中 | ❌ 太长 |
| 1 | 号段 → 打乱字符表 → Base62 | 6 | 天然 | ❌ 单表替换密码，频率分析即破 | ❌ |
| 2 | 号段 → 模乘置换 → Base62 | 6 | 天然（双射） | ⚠️ 仅混淆级 | ❌ 见下 |
| 3 | 号段 → Feistel FPE → Base62 | 6 | 天然（双射） | ✅ 密钥级 | ⭕ 备选，已实现 |
| 4 | **随机 6 位 + BF 判重 + 唯一索引兜底** | 6 | 靠判重 | ✅ 强 | ✅ **采用** |

### 为什么雪花算法出局（这是纯数学，答不上来很难看）

```
Snowflake = 1(符号) + 41(毫秒时间戳) + 10(机器) + 12(序列) = 64 bit
量级 ≈ 2^63 ≈ 9.22e18
ceil(log62(9.22e18)) = ceil(63 / 5.954) = 11 位     ← 已用代码验算
```

而 bit.ly / t.cn 都是 7 位。更糟的是短码长度**会随时间增长**（实测：第 1 天 9 位，第 1 年 10 位）。

**根因（这句话是杀手锏）**：短码长度 = log62(ID 最大值)，所以短码要短就要求 ID 空间被**密集**利用。
雪花的时间戳位是**稀疏**分配——绝大多数 ID 值永远不会被使用，纯粹浪费编码空间。

**但雪花不是白学的**：本项目保留了号段发号器作为 `t_link` **主键**来源（趋势递增，避免页分裂）。
**把"唯一性"（发号器）和"不可猜测性"（短码生成）解耦成两套机制**，是这个项目最值得讲的架构判断之一。

### ★ 为什么模乘置换只算"混淆"不算"安全"（实测已证实）

```java
enc(id) = (id * P + K) mod N        // N = 62^6, P = 1000000007, K = 20260726
```

它看起来很美：双射（不冲突、不需判重、不浪费编码空间）、可逆、两次整数运算。**但**：

```
enc(id+1) - enc(id) ≡ P  (mod N)
```

攻击者只要**连续调用两次创建接口**，拿到两个短码解码相减就直接得到 P；
再用任意一个已知 (id, code) 对反推出 K。**整个置换在两次 API 调用内被完全破解。**

实测验证（id=0/1/2）：

```
密文        = 20260726, 1020260733, 2020260740
连续差值    = 1000000007, 1000000007        ← 恒等于 P，一目了然
```

对照 Feistel（同样 id=0/1/2/3）：差值 `54286767085, -39861784235, 312112642` —— 无规律。

### 为什么最终选第 4 级而不是第 3 级 Feistel

Feistel 是更"优雅"的答案（双射、无需判重、可逆），我也实现了它（`FeistelCipher`，含
cycle-walking 处理 `2^36 = 687 亿 > 62^6 = 568 亿` 的越界，期望迭代 1.21 次）。
但随机+判重：

1. **碰撞概率可忽略**：空间 568 亿，已有 1000 万条时单次撞车概率 = `1e7/5.68e10 = 0.018%`；
   重试 5 次全撞的概率 ≈ `1.8e-19`
2. **实现量是 Feistel 的 1/4**
3. **让布隆过滤器的"判重"用途变成真正必要的**，整体设计更自洽（见 ADR-004）

**放弃了什么**：失去短码 → ID 的可逆性，因此分片方案只能选异构索引表而不能选基因法（见 ADR-005）。
如果未来需要反解，切到 `FeistelCipher` 即可，接口已就位。

**另一个细节**：用 `SecureRandom` 而不是 `Random`。`Random` 是线性同余，
从几个输出就能推出内部 state 进而预测后续短码——那等于把辛苦换来的抗枚举又送回去了。

## ADR-004 布隆过滤器的三个决策

**背景**：需要防缓存穿透；同时随机短码方案需要判重。

### (1) 两个用途都需要，且这是设计自洽性的考点

| 短码方案 | 用途 A 防穿透 | 用途 B 生成判重 |
|---|---|---|
| 号段 + 置换 / Feistel（双射） | ✅ | ❌ 不需要（天生无冲突） |
| **随机生成（本项目）** | ✅ | ✅ **必需** |

面试官会考：「你既然用号段+置换保证了唯一，为什么还要 BF 判重？」——
答不上来就暴露是拼凑的。本项目两个用途都用，因为选了随机方案。

### (2) ★ 写入顺序必须是"先写 BF，后落库"

BF 的误差是**单向**的：**可能误报"存在"，绝不误报"不存在"**。

| 顺序 | 失败后果 | 严重度 |
|---|---|---|
| 先落库 → 后写 BF | BF **漏位** → **合法短链永久 404** | 🔴 生产事故 |
| **先写 BF → 后落库** | BF **多位** → 那个不存在的短码多穿透一次 DB，被空值缓存兜住 | 🟢 可接受 |

**决策**：先写 BF。**让失败方向与 BF 本身的误差方向一致。**

### (3) BF 判重防不住并发竞态 → DB 唯一索引是必需的兜底

两个请求可能同时 `contains` 都返回 false，同时 `add`，同时插入。
`uk_short_uri` 不是冗余，是**必需**的。

### 容量与内存（面试爱问"占多少内存"）

```
m/n = -ln(p) / (ln2)²        k = (m/n) · ln2

n=1000万, p=0.01%  →  19.17 bit/元素,  22.9 MiB,  k=13     ← 本项目
n=1亿,    p=0.01%  →  19.17 bit/元素, 228.5 MiB,  k=13
n=1亿,    p=1%     →   9.59 bit/元素, 114.3 MiB,  k=7
```

**放弃了什么**：BF 不支持删除 → 短链删除后位无法清除 → 假阳性率单调上升。
对策是双 BF 滚动重建（定时用 DB 全量构建新 BF 后切流）。
Counting BF 需 4-8 倍内存，Cuckoo Filter 实现复杂——都不值当。

**顺着这个约束推出了 ADR-006。**

## ADR-005 分库分表：异构索引表 vs 基因法（Week 4）

**背景**：两条查询链路要的分片键互相冲突。

```
跳转链路（QPS 极高）：WHERE short_uri = ?     → 必须按 short_uri 分片
管理链路（QPS 低）：  WHERE gid = ? ORDER BY  → 想按 gid 分片
```

按 `short_uri` 分片 → 管理链路要**广播查询 16 个分片再归并排序分页**；
按 `gid` 分片 → **跳转链路要广播查询**（主链路，绝对不能接受）。

**考虑过的方案**

| 方案 | 两条链路都单分片 | 可扩容 | 需双写 | 结论 |
|---|---|---|---|---|
| 基因法（把 gid hash 嵌进短码） | ✅ | ❌ | ❌ | ❌ |
| **异构索引表 `t_link_goto`** | ✅ | ✅ | ✅ | ✅ 采用 |
| 管理链路剥离到 ES | ✅ | ✅ | ✅ | ⭕ 更重，时间不够 |

**决策**：主表按 `short_uri` 分 2 库 × 8 表；另建 `t_link_goto(gid, short_uri)` 按 `gid` 分片，
创建时双写，一致性用**本地消息表**（同库事务写 `t_link` + 消息记录，定时补偿投递）。

**为什么不选基因法**：
> 基因法的优点是不需要双写、没有一致性问题；但它把**分片数固化在了短码里**，
> 一旦要扩容就得重新生成所有历史短码，而**历史短码可能已经印在海报和二维码上了，改不了**。
> 异构索引表多了一次查询和一套双写补偿，换来的是可扩容。对这个场景，可扩容更重要。

另外两个理由：
1. 异构索引表是**电商订单表的经典做法**（买家维度 + 卖家维度双写），通用性远高于基因法
2. 本项目的短码是随机生成的、**不可逆**，基因法需要从短码反解出基因位，技术上就不成立（见 ADR-003）

**放弃了什么**：管理链路变成两步查询（先查索引表拿 short_uri 列表，再回查主表）；
多一套双写补偿的运维成本。

**验收标准**：打开 ShardingSphere SQL 日志，跳转和列表查询都**不能出现 16 条 SQL**。

## ADR-006 短码不回收复用

**背景**：短链过期/删除后，短码要不要放回池子重复使用？

**决策**：**不回收。**

**三层理由**（能自己推出这个结论说明想通了）：

1. **业务事故风险**：老的二维码、海报、短信、印刷品上还印着这个短码。
   复用后老海报会跳到别人的活动页——这是真实的线上事故。
2. **技术约束**：BF 不支持删除位（ADR-004），复用会让 BF 语义混乱。
3. **根本不需要**：62^6 = 568 亿，按 1 亿/年用 **568 年**。

**推理链条本身就是面试素材**：从"BF 不支持删除"这个技术约束，
反推出"短码不回收"这个产品决策，并用容量数字证明这个决策没有代价。

**配套决策**：过期/删除用**逻辑删除** `del_flag`（保留统计数据）；
过期短链访问返回 `410 Gone` + 失效落地页，**不要 302 到首页**（用户会困惑）。

## ADR-007 幂等：默认幂等 + `forceNew` 开关（Week 4 补分片下的全局去重）

**背景**：同一长链重复创建，返回同一短码还是新短码？

**这道题没有唯一正确答案，能说清"取决于业务语义"才是满分**：

- **bit.ly 的行为**：同账号 + 同长链 → 返回同一短码
- **营销场景恰恰相反**：同一落地页要生成 20 个不同短码，分投微信/微博/抖音/短信做**渠道归因**

**决策**：默认按 `(gid, url_hash)` 幂等，提供 `forceNew=true` 支持渠道归因。

**实现细节**：
- 用 `url_hash BINARY(16)` 而不是 `origin_url` 建索引 —— 因为 `VARCHAR(2048)` utf8mb4 = 8192 字节，
  **超过 InnoDB 索引键 3072 字节上限，建不了索引**
- `BINARY(16)` 比 `CHAR(32)` 存十六进制省一半空间

**⚠️ 分库分表下的坑（Week 4 要解决）**：唯一索引只在**单个分片内**生效。
`t_link` 按 `short_uri` 分片，而幂等判断按 `url_hash` —— 同一长链两次创建会拿到不同 `short_uri`、
落到不同分片，`uk_gid_url_hash` 拦不住。

三个解法：
1. 单独的去重表按 `url_hash` 分片（本质又是一张异构索引表）
2. Redis `SETNX url_hash → short_uri`（快，但要处理 Redis 挂了的情况）
3. 承认极端并发下可能生成两个短码，做成"最佳努力幂等"（业务上可接受）

## ADR-008 缓存一致性：落在真实需求上，而不是套八股

**背景**：原方案列了 Cache Aside / 延迟双删 / Canal 监听 binlog。

**问题**：**短码 → 长链的映射近乎不可变**。面试对话会变成：
> 面试官："你的短链会修改吗？" 你："基本不会。"
> 面试官："那你的延迟双删在解决什么问题？" 你：（卡住）

**决策**：把一致性问题落在**真实存在**的三处：

| 场景 | 需求强度 | 方案 |
|---|---|---|
| **短链禁用/封禁/删除** | 🔴 硬需求，有时效 SLA | Redis DEL + Pub/Sub 广播清本地缓存 + Caffeine 短 TTL 兜底 |
| **企业改跳转目标** | 🟡 真实低频需求 | 这里才需要 Cache Aside / 延迟双删 |
| **访问计数最终一致** | 🟡 | Redis 计数 → 定时批量 upsert 落库 |

**为什么"广播 + 短 TTL"要两层**：Redis Pub/Sub 是 fire-and-forget，**不保证送达**
（订阅端正在重连时消息就丢了，没有重试）。
- 广播 → 99% 情况 100ms 内生效
- 短 TTL(5s) → 最坏情况 5 秒必定生效

**把代价量化出来**（这是区分"做过"和"背过"的分水岭）：
> "本地缓存 TTL 5 秒意味着封禁最多 5 秒后生效。我评估过：对钓鱼链接，
> 5 秒内多放过的点击量在可接受范围。如果业务要求 0 延迟就得放弃本地缓存，
> 代价是 QPS 从 3.8w 掉到 1.2w。我选了 5 秒。"

**为什么不用 Canal**（只讲不做）：
> "Canal 订阅 binlog 的优点是业务代码零侵入、天然解决双写不一致；
> 缺点是引入 Canal + MQ 的运维复杂度，而且缓存更新有 binlog 延迟。
> 我这个场景的变更频率极低，Pub/Sub 广播 + 短 TTL 已经够了。
> 数据量再上一个量级、或者有多个下游都要感知变更时，Canal 才值得。"

## ADR-009 MQ 只用在统计链路，不用在创建链路

**背景**：原方案是"写高峰用 MQ 异步落库削峰"。

**这个方案有一个必然的 bug**：

```
创建 → 发 MQ → 立即返回短码 → 用户 100ms 内就访问 → 缓存和 DB 都还没有 → 404
```

而"生成完立刻群发"正是营销短链的典型用法，所以这个 404 **必然**发生，不是概率问题。

**更根本的问题是读写比**：短链创建 : 访问 ≈ **1 : 500 ~ 1 : 1000**。
创建 QPS 本来就低（几百到几千），**根本不需要削峰**。

**决策**

| 链路 | 做法 | 理由 |
|---|---|---|
| **创建短链** | **全同步**：落库 + 写 BF + 预热缓存都做完才返回 | 用创建时的几毫秒换跳转时的确定性，返回即可读 |
| **批量创建**（营销一次生成 100 万条） | 异步任务 + `rewriteBatchedStatements=true` 批量 insert（1000 条/批），返回 `taskId` 轮询进度 | 这才是"批量 insert 削峰"的正确用法，也是真实企业场景 |
| **访问统计** | **异步投 MQ**，Redis 计数 + 定时批量 upsert | 这里 QPS = 跳转 QPS，是真正需要削峰的地方 |

**统计链路的不可动摇契约**：**统计绝不能影响跳转。**
MQ 发送失败降级为本地有界队列暂存（有界很重要，无界会 OOM——那就从"统计降级"变成"服务挂掉"）。

**MQ 选型**：RabbitMQ。理由见 ADR-001（RocketMQ starter 还卡在 Boot 2.7 基线）。

## ADR-010 302 而不是 301

**背景**：跳转用哪个状态码。

| | 301 永久 | 302 临时 |
|---|---|---|
| 浏览器缓存 | 强缓存，**不回源** | 每次回源 |
| 服务器压力 | 小 | 大 |
| 访问统计 | ❌ 丢失大部分 | ✅ 完整 |
| 目标可变更 | ❌ | ✅ |
| **风控封禁** | ❌ **已缓存的用户拦不住** | ✅ 立即生效 |

**决策**：302。

**决定性理由是风控，不是统计**（大多数人答"因为要统计"，这个答法档次低一档）：
> 短链被举报为钓鱼后必须能立即断掉。用 301 的话浏览器已经强缓存了，
> 后续请求根本不到服务器，**你永远拦不住已经缓存过的用户**。
> 把风控优先级放在服务器压力之上，是这里的决定性判断。

**两个能加深度的补充**：
1. 商业平台常用 **`301 + Cache-Control: private, max-age=90`** 组合拳——
   既拿到 301 的减压效果，又把缓存窗口压到 90 秒
2. **307/308** 严格保留请求方法和 body（301/302 历史实现会把 POST 降级成 GET）。
   短链 99% 是 GET 所以 302 够用；但用在 API 回调 / Webhook 上必须 307

**放弃了什么**：放弃了 301 的服务器减压收益，代价由多级缓存补回来。

**绝对不要**用 HTML `meta refresh` 或 JS `location.href` 跳转
（多一个完整 RT + 页面渲染，延迟从 ~10ms 变 ~300ms，SEO 差，部分 App 内嵌 WebView 不跟随）。

## ADR-011 号段取号必须"每次重试开新事务"（真实踩过的 bug）

**背景**：`DbSegmentStore` 用乐观锁 CAS 推进 `max_id`，失败重试。

**最初的写法**：方法上加 `@Transactional(propagation = REQUIRES_NEW)`，方法内部写重试循环。

**★ 这在 MySQL 默认的 REPEATABLE READ 下是错的**：

```
第 1 次：SELECT 读到 version = 5  →  UPDATE ... WHERE version = 5  →  0 行（别人抢先了）
第 2 次：SELECT 又读到 version = 5   ← 同一事务里的快照读，看不到别人的提交！
        UPDATE ... WHERE version = 5  →  又是 0 行
...重试到上限，抛异常
```

REPEATABLE READ 下同一事务内的重复 SELECT 返回同一快照，**所以重试永远不可能成功**。
表现是"并发一高发号器就报 CAS 失败"，但去看 SQL 又完全正确——**非常难查**。

**决策**：用 `TransactionTemplate`（`PROPAGATION_REQUIRES_NEW`）让**每次尝试各自开一个新事务**，
重试循环放在事务外面。加 `1/2/4/8/16 ms` 指数退避避免多实例反复对撞。

**考虑过的替代方案**

| 方案 | 结论 |
|---|---|
| 把方法隔离级别降到 READ COMMITTED | ❌ 让"隔离级别"成为隐式依赖，换库或改全局配置就静默失效 |
| 改用 `SELECT ... FOR UPDATE` | ❌ 行锁持有到事务提交，取号是创建链路的公共前置，会让整条链路排队 |
| **每次尝试开新事务（TransactionTemplate）** | ✅ 采用，显式且不依赖隔离级别 |

**为什么 REQUIRES_NEW 也是必需的（另一个坑）**：取号必须独立提交。
如果被业务事务裹住，业务回滚会把 `max_id` 的推进一起回滚，
而内存 buffer 已经把这些号发出去了 → **号段重复分配**。

**顺带说清一件事：为什么 `UPDATE SET max_id = max_id + ?` 这种相对赋值是安全的**

乍看有隐患：SELECT 读到 M，UPDATE 时 max_id 可能已被别人改成 M'，
于是 max_id 变成 M' + step，而返回的区间基于旧的 M —— 会重叠。

`WHERE version = ?` 正是为了堵住它：别人改过则 version 变了，UPDATE 影响 0 行，走重试。
**版本号不是可选的装饰，它是这段逻辑正确性的地基。**

**数据依据**：`DbSegmentStoreTest` 用内存模型模拟 MySQL 的快照读 / 当前读两种语义：
64 线程 × 20 次取号，1280 个区间**任意两个都不重叠**，且"末段上界 == 段数 × step"
（证明既无空洞也无重叠）。原始 bug 已固化成回归测试
`retryInsideOneTransactionCanNeverSucceed`，防止以后有人"顺手"把 `@Transactional` 加回去。

## ADR-012 压测方法论：请求分布必须用 Zipf

**背景**：要给"高并发"这个标题拿到可信数字。

**★ 核心决策：请求分布用 Zipf(α=1.0)，不用均匀随机**

真实短链流量极度长尾：少数热门链接占绝大部分点击。均匀随机每次都打一个几乎没被访问过的
短码，本地缓存永远不命中——**测的是一个现实中不存在的场景，并且系统性低估缓存效果**。

数值计算（N=1000 万，`benchmark/cache_math.py`）：

| 请求分布 | 10,000 条本地缓存的 L1 命中率 |
|---|---|
| 均匀随机 | **0.10%** |
| Zipf α=1.0 | **58.62%** |
| Zipf α=1.2 | **89.00%** |

**差 586 倍。** 用均匀随机压测，你会得出"本地缓存没用"的错误结论。

**衍生决策：`maximumSize` 从 10,000 改成 100,000**

这个值原来是拍的，现在是算的：

| maximumSize | L1 命中率 | 内存 | 期望延迟 |
|---|---|---|---|
| 10,000 | 58.6% | 2.4 MB | 207 us |
| **100,000** | **72.4%** | **23.8 MB** | **138 us** |
| 500,000 | 82.1% | 119 MB | 90 us |

多 21 MB 换 +13.8pp 命中率、延迟 -33%，对 JVM 是白菜价。再往上边际收益明显递减。

**★ 必须分清的两个数（混着说会被面试官问穿）**

| 指标 | 含义 | 量级 |
|---|---|---|
| **L1 命中率** | Caffeine 命中 / 总请求 | Zipf α=1.0 下约 72% |
| **整体缓存命中率** | (L1 + Redis) / 总请求 | 99.9%+（Redis 装得下全部 1000 万条） |

简历上写哪个都行，但必须标清楚是哪个。

**其他配套决策**

1. **可复现是前提**：固定 `--seed`，预生成 `requests.txt`，wrk 各线程用**确定性偏移**
   （`(tid-1)*9973 % n`）而不是随机起点。否则"优化前 / 优化后"打的不是同一批请求。
2. **每轮前清本地缓存**（`POST /admin/cache/local/clear`），否则上轮预热让本轮虚高。
3. **★ 灌完数据必须重建布隆过滤器**（`POST /admin/bloom/rebuild`）。
   否则 BF 里没有这些短码，全部请求被判"一定不存在"直接 404 —— 而 **QPS 会高得离谱**
   （根本没查缓存和 DB），极易误以为优化大成功。`redirect.lua` 会自动检查 302 占比并报警。
4. **主动声明放宽的持久化设置**：MySQL `innodb_flush_log_at_trx_commit=2`、Redis 关 AOF。
   主动说出来比被问出来强一百倍。
5. **压测时先关限流和 SQL 日志**，否则测的是限流器吞吐 / 你会误判瓶颈在 DB。

**放弃了什么**：Zipf CDF 需要 O(N) 内存（1000 万条约 80 MB），生成请求日志慢一些。
换来的是数据可信。

## ADR-013 布隆过滤器重建必须"双 BF 滚动"而不是原地清空

**背景**：BF 不支持删除位（ADR-004），删短链后假阳性率单调上升，需要定时全量重建。
另外压测灌完种子数据也必须重建一次。

**★ 原地 `delete()` 后重填有一个致命窗口**：重建期间 BF 是空的或不完整的，
此时所有跳转请求都会被判"不存在" → **全站短链在重建期间集体 404**。

**决策**：写新的 → 切指针 → 删旧的。

```
1. 往 bloom:uri:v{N+1} 灌 DB 全量数据（此时线上仍在读 v{N}）
2. 灌完，把版本号 SET 到 N+1（一次原子操作）
3. 延迟后删除 v{N}（让正在处理中的请求走完）
```

**任何"清空后重建"的缓存 / 索引都有这个问题，不只是布隆过滤器。**
能主动指出这一点，比会背"BF 不支持删除"高一个档次。

**配套的两个设计**

1. **版本号必须缓存在本地**（`BloomFilterHolder` 的 volatile 字段）。
   每次判断短码都去 Redis 读版本号，等于给跳转链路凭空加一次网络往返——
   而这条链路的全部优化都是在省这次往返。本实例重建后零延迟切换，
   其他实例靠 30 秒定时对版本。
2. **30 秒滞后为什么可以接受**：新 BF 是旧 BF 的超集，旧 BF 只少了重建期间新建的那几条。
   而这几条已经被创建链路的"先写 BF"消掉了（ADR-004）——新建短链在任何版本的 BF 里都存在。
   **两处设计正好互补，这不是巧合，是"先写 BF"这个顺序带来的额外收益。**

3. **游标分页而不是 `LIMIT offset`**：offset 很大时 MySQL 要扫描并丢弃前 offset 行，
   1000 万行时最后几页慢到不可接受（经典深分页问题）。而且 `id` 和 `short_uri`
   必须一次查出来——分成两条 SQL 等于把整表扫两遍。
