# Part 2 · 技术方案里的 3 个硬错误 + 4 个深度不足

## 2.1 🔴 硬错误一：**雪花算法不能直接用来生成短码**（这是纯数学问题，答不上来会很难看）

你写「分布式 ID 生成（雪花算法 / 号段模式发号器）」，把两者并列成"可选方案"。但在短链场景，**雪花算法直接出局**，原因是短码长度：

```
Snowflake: 1(符号) + 41(毫秒时间戳) + 10(机器) + 12(序列) = 64 bit
ID 量级 ≈ 2^63 ≈ 9.22e18

需要的 Base62 位数 = ceil(log62(9.22e18)) = ceil(63 / log2(62)) = ceil(63 / 5.954) = 11 位
```

**即 11 位短码。而 bit.ly 是 7 位，t.cn 是 7 位。你的"短"链接比人家长 57%。**

更糟的是：即使你把 epoch 设成 2026-01-01，
- 第 1 天：`ID ≈ 8.64e7 << 22 ≈ 3.62e14` → **9 位**
- 第 1 年：`ID ≈ 3.15e10 << 22 ≈ 1.32e17` → **10 位**

**短码长度会随时间增长且不一致**，这在产品上是不可接受的。

### 根因（这句话是你面试时的杀手锏）

> **短码长度 = log62(ID 最大值)。所以短码要短，就要求 ID 空间被"密集"利用。雪花算法的时间戳位是"稀疏"分配——绝大多数 ID 值永远不会被使用，纯粹在浪费编码空间。号段模式从 1 开始连续递增，是密集分配。所以在短链这个"编码长度敏感"的场景，号段模式（或 Hash）胜出，雪花算法是错误选型。**

数字对比：

| 方案 | ID 空间利用 | 6 位 Base62 容量 | 结论 |
|---|---|---|---|
| UUID (128bit) | 极稀疏 | 需 22 位 | 出局 |
| 雪花 (64bit) | 稀疏 | 需 10-11 位 | 出局 |
| DB 号段（从 0 连续） | **密集** | 62^6 = **568 亿** | ✅ |
| Hash(长链) 截断 42bit | 密集但有碰撞 | 需处理冲突 | ✅ 备选 |

> 62^5 = 916,132,832（9.16 亿）
> 62^6 = 56,800,235,584（**568 亿**）
> 62^7 = 3,521,614,606,208（3.5 万亿）
>
> 按 1 亿条/年生成，6 位够用 **568 年**。所以 6 位是正确答案，7 位是保险。

📌 **一个重要的收尾（否则你的方案会不自洽）**：这一节证明了"雪花不能做短码"，但**号段发号器并不会因此被废弃**——它在最终方案里承担的是 **`t_link` 的主键**（趋势递增，避免 InnoDB 页分裂，见 5.3），而短码本身会走 2.2 讨论的抗枚举路径。
> **把"唯一性"（发号器）和"不可猜测性"（短码编码）解耦成两套机制，是这个项目最值得讲的架构判断之一。**

**但是**——雪花不是白学的。面试时的正确讲法是：

> "我最初选的是雪花算法，写完才发现 Base62 编码后是 11 位，短码太长。于是回头算了一遍：短码长度取决于 ID 空间的稠密度，雪花的时间戳位让 ID 极度稀疏。所以我换成 DB 号段模式，短码稳定 6 位。雪花我保留在了另一个地方——统计明细表的主键，那里不要求短，要求趋势递增和无中心依赖。"

**这个"我踩了坑并且推理出根因"的叙事，比一开始就选对更值钱。**

## 2.2 🔴 硬错误二：号段递增 → Base62 → **短码可被顺序枚举**（安全漏洞，你完全没提）

号段模式的 ID 是连续的，直接 Base62 编码后，相邻创建的短链短码也相邻。爬虫写个循环就能遍历你系统里**所有**短链。

这不是理论风险：早年 bit.ly / goo.gl 上就被人批量爬出大量本以为"只有拿到链接的人才能看"的 Dropbox 分享链、Google Docs 私密文档、医疗预约页面。**短链的"不可猜测性"本身就是一层访问控制。**

### 四级解法阶梯 —— **这个阶梯本身就是最好的面试素材，因为它记录了你的推理过程**

#### 第 1 级：只打乱 Base62 字符表 ❌ 安全性 ≈ 0
固定的字符替换 = 单表替换密码，频率分析或几个已知样本就能破。**但要知道它为什么不行**，这本身是考点。

#### 第 2 级：模乘置换（Modular Multiplicative Permutation）⚠️ **能防外人，防不住"能调你接口的人"**

```java
private static final long N = 56_800_235_584L;   // 62^6
private static final long P = 1_000_000_007L;    // 与 N 互质
private static final long K = 20_260_726L;       // 偏移量

long scrambled = (id * P + K) % N;               // 编码
String code = base62Fixed(scrambled, 6);         // 定长 6 位
long id = ((scrambled - K + N) % N) * P_INV % N; // 解码（P_INV = 15351586039）
```

`62^6 = (2·31)^6 = 2^6 · 31^6`，所以 P 只要不被 2 和 31 整除即可（`1000000007` 是奇数，`mod 31 = 23`，✅ 已验算 `gcd(P,N)=1`，模逆元存在，往返可逆）。

优点：**双射**（不冲突、不需判重、不浪费编码空间）、**可逆**（基因法分片需要）、两次整数运算无性能损耗。

**🔴 但它有一个致命弱点，你必须自己主动说出来（否则被面试官指出就很被动）：**

> **连续两个 ID 的密文之差恒等于 P（mod N）。**
> 攻击者只要连续调用两次你的创建接口，拿到两个短码，解码相减就直接得到 P；再用任意一个已知 (id, code) 对反推出 K。**整个置换在两次 API 调用内被完全破解。**
>
> （我验算过：id = 0/1/2 的密文是 20260726 / 1020260733 / 2020260740 —— 差值恒为 1000000007，就是 P 本身。）

所以模乘置换的正确定位是 **obfuscation（混淆），不是 security（安全）**。它能挡住"随手 ++ 试一下"的路人，挡不住任何认真的攻击者。

#### 第 3 级：Feistel 网络（FPE 格式保留加密）✅ **推荐主方案**

4 轮 Feistel + 带密钥的轮函数（HMAC-SHA256 截断），把 36 bit 的域（`2^36 > 62^6`）加密后映射回 6 位 Base62。约 40 行代码，**并不比模乘置换难多少，但它是真正安全的**。

```java
// 域拆成左右各 18 bit
long feistelEncrypt(long x) {                 // x < 2^36
    long L = x >>> 18, R = x & 0x3FFFF;
    for (int round = 0; round < 4; round++) {
        long F = roundFunc(R, round) & 0x3FFFF;   // HMAC(key, R‖round) 截 18 bit
        long tmp = L ^ F;
        L = R; R = tmp;
    }
    return (L << 18) | R;
}
// 解密：反向跑 4 轮（Feistel 结构天然可逆，轮函数不需要可逆）
```

三个优点：**双射**（无冲突、无需判重）、**可逆**、**密钥安全**（不知道 key 就无法从任意数量的样本推出映射）。

⚠️ 工程细节：`2^36 = 687 亿 > 62^6 = 568 亿`，加密结果可能落在 `[62^6, 2^36)` 之外的区间。用 **cycle-walking** 解决：结果超出值域就再加密一次，直到落入值域内（Feistel 是置换，所以循环必然终止，期望迭代次数 ≈ 1.2 次）。**这个细节答出来非常亮。**

#### 第 4 级：直接生成随机短码 + 判重重试 ✅ **最简单，也完全安全，时间紧就选这个**

```java
for (int i = 0; i < 5; i++) {
    String code = randomBase62(6);                 // SecureRandom
    if (!bloomFilter.contains(code)) {             // BF 说"不存在"⇒ 一定不存在
        bloomFilter.add(code);
        try { insert(code, url); return code; }    // DB 唯一索引兜住并发竞态
        catch (DuplicateKeyException e) { /* 极小概率，重试 */ }
    }
}
throw new IllegalStateException("短码空间告急");
```

碰撞概率算得出来：空间 568 亿，已有 1000 万条时，单次生成撞车概率 = `1e7 / 5.68e10 = 0.018%`，可忽略；重试 5 次仍失败的概率约 `1.8e-19`。

**它的两个额外好处**：
1. **让布隆过滤器的第二个用途（生成时判重）变成真正必要的**，整个设计因此更自洽（见 2.4-(1)）
2. **DB 唯一索引是必需的兜底**——两个并发请求可能同时通过 BF 检查（BF 无锁），只有唯一索引能拦住。**"我知道 BF 判重防不住并发竞态，所以唯一索引是必需的而不是冗余的"是一个很好的深度点。**

代价：失去可逆性（但用异构索引表分片就不需要可逆），多一次 BF 查询。

**无论选哪个，面试时都要把这个 4 级阶梯完整讲一遍。** 面试官听到的不是"我用了某个算法"，而是"这个人会自己评估方案的安全边界"——后者稀缺得多。

## 2.3 🔴 硬错误三：**MQ 异步落库 + 同步返回短码 = 必然的 404**

你写「写高峰怎么用 MQ 异步削峰」。这条链路展开是：

```
创建请求 → 发号 → 生成短码 → 投 MQ → 立即返回短码给用户
                                       ↓（异步，可能延迟 10ms～10s，MQ 堆积时更久）
                                    消费者落库

用户/群发系统拿到短码后 100ms 内就访问 → 缓存没有、DB 没有 → 404
```

**营销短链的典型用法就是"生成完立刻群发"，所以这个 404 是必然会发生的，不是概率问题。** 面试官问一句"你异步落库，用户拿到短码马上访问怎么办"，这个方案就崩了。

### 更根本的问题：你把 MQ 用在了错误的链路上

**短链系统的读写比通常是 100:1 ~ 1000:1。** 创建短链的 QPS 天然很低（一个营销活动生成几万条链接，但这几万条链接会被点击几百万次）。

> **需要削峰的从来不是"创建"，而是"访问统计"。**

你的架构重心偏了。修正方案：

| 链路 | 正确做法 | 理由 |
|---|---|---|
| **创建短链** | **同步落库 + 同步写缓存 + 同步写布隆过滤器**，然后返回 | QPS 本来就低（几百到几千），不需要削峰。同步保证了"拿到短码即可访问" |
| **批量创建**（真实需求：营销一次生成 100 万条） | 异步任务 + `rewriteBatchedStatements=true` 批量 insert（1000 条/批），返回 `taskId`，前端轮询进度，完成后打包 CSV 下发 | 这才是"批量 insert 削峰"的正确用法，而且是真实企业场景 |
| **访问统计** | **异步投 MQ**，消费端 Redis 计数 + 定时批量 upsert 落库 | 这里 QPS 高（等于跳转 QPS），是真正需要削峰的地方 |

**面试话术**：
> "我一开始也想在创建链路上用 MQ 削峰，写到一半发现一个必然的 bug：异步落库时用户拿到短码立刻访问会 404。回头算读写比，发现创建和访问是 1:1000，创建根本不需要削峰。所以我把 MQ 挪到了统计链路——那里 QPS 等于跳转 QPS，而且统计允许秒级延迟和少量误差。批量创建场景我单独做了异步任务 + 批量 insert。"

## 2.4 ⚠️ 深度不足一：布隆过滤器，你混了两个用途，且漏了 4 个致命细节

### (1) 两个用途必须分清（自洽性考点）

- **用途 A：防缓存穿透** —— 判断 `short_uri` 是否存在过，拦掉恶意构造的不存在短码
- **用途 B：生成时判重** —— 判断某个候选短码是否已被占用

**关键：用途 B 需不需要，取决于你 2.2 选了哪一级：**

| 短码方案 | 用途 A | 用途 B | 理由 |
|---|---|---|---|
| 号段 + 模乘置换 / Feistel（**双射**） | ✅ 需要 | ❌ **不需要** | 双射保证不同 ID 必得不同短码，天生无冲突 |
| 随机生成 | ✅ 需要 | ✅ **必需** | 随机会撞车，必须判重 |
| Hash(长链) 截断 | ✅ 需要 | ✅ **必需** | Hash 有碰撞 |

面试官会考这个自洽性：「你既然用号段+置换保证了唯一，为什么还要布隆过滤器判重？」—— 答不上来就暴露了是拼凑的。**主动说清"我这个方案里 BF 只用于 A / 同时用于 A 和 B，因为……"，说明整套设计是你自己想通的。**

⚠️ 用于 B 时还有一个陷阱：**BF 判重防不住并发竞态**（两个请求同时查 BF 都得"不存在"，同时写入）。所以 **DB 唯一索引是必需的兜底，不是冗余**。

### (2) 🔴 最致命的细节：**写入顺序必须是「先写 BF，后落库」**

新建短链必须写入 BF，否则用户拿到短码后访问时被 BF 拦掉 → **合法短链永久 404**，这是生产事故级 bug。

关键推理（这是一道很漂亮的面试题）：

> 布隆过滤器的误差是**单向**的：**可能误报"存在"，绝不会误报"不存在"**。
> - 若「先落库、后写 BF」：落库成功但 BF 写失败 → BF **漏位** → 合法短链永久不可达 ❌
> - 若「先写 BF、后落库」：BF 写成功但落库失败 → BF **多位** → 最坏结果只是这个不存在的短码会多穿透一次到 DB（然后被空值缓存兜住）✅
>
> **所以顺序必须是先写 BF 后落库——让错误方向和 BF 本身的误差方向一致。**

### (3) 容量必须算出来（面试官爱问"占多少内存"）

标准公式：
```
每元素比特数  m/n = -ln(p) / (ln2)²
哈希函数个数  k   = (m/n) · ln2
```

| 数据量 n | 误判率 p | m/n | 内存 | k |
|---|---|---|---|---|
| 1000 万 | 0.01% (1e-4) | 19.17 bit | **22.9 MiB** | 13 |
| 1 亿 | 0.01% | 19.17 bit | 228.5 MiB | 13 |
| 1 亿 | 1% | 9.59 bit | 114.3 MiB | 7 |

（以上已用代码验算过。）学生项目用 **1000 万 / 0.01% / ≈23 MiB / k=13** 这组数最合理，面试时能直接报出来，还能顺手说清公式怎么来的。

### (4) 不支持删除 → 容量单调恶化

短链删除/过期后，BF 的位不能清（会影响其他元素）→ 有效元素变少但占位不变 → **假阳性率单调上升**。

三个解法（讲取舍）：
- **双 BF 滚动重建**：定时用 DB 全量数据构建新 BF，构建完切流，旧 BF 延迟销毁。（推荐，简单可靠）
- **Counting Bloom Filter**：每位改成计数器，支持删除，代价是 4-8 倍内存
- **Cuckoo Filter**：原生支持删除，空间效率也更好；代价是实现复杂、插入可能失败

**顺着这个还能推出一个结论**（见 4.4）：**短码不应该回收复用**，所以 BF 里的元素只增不减，"删除"这个需求其实不存在——只有"过期短链的记录还在，只是跳转时返回失效页"。**能推到这一步，说明你想通了。**

### (5) 本地 BF vs Redis BF

| | Guava BloomFilter（本地） | Redisson RBloomFilter（Redis） |
|---|---|---|
| 延迟 | 纳秒级 | 1 次网络 RT |
| 多实例一致性 | ❌ 各自一份，A 实例新建的短链 B 实例拦掉 | ✅ 共享 |
| 重启 | ❌ 丢失，需全量重建 | ✅ 持久 |
| 内存 | 23MB × 实例数 | 23MB（Redis 侧） |

**结论：多实例部署必须用 Redis BF。** 想优化延迟就做两层：本地 BF 只做"一定不存在"的快速拦截（要求本地 BF 是 Redis BF 的子集，靠启动全量加载 + 订阅增量保证），Redis BF 做权威判断。**5 周时间下建议只做 Redis BF，把两层方案作为"我设计过但没实现"来讲。**

## 2.5 ⚠️ 深度不足二：分库分表 —— 你只说了"要分"，而**分片键才是这题的全部难点**

短链有两条查询链路，它们要的分片键**互相冲突**：

```
跳转链路（QPS 极高）：SELECT origin_url FROM t_link WHERE short_uri = ?
管理链路（QPS 低）：  SELECT * FROM t_link WHERE gid = ? ORDER BY create_time LIMIT ?
```

- 按 `short_uri` 分片 → 跳转单分片命中 ✅，但管理链路要**广播查询所有分片再归并排序分页** ❌（分片数一多就崩）
- 按 `gid` 分片 → 管理链路 ✅，但**跳转链路要广播查询** ❌❌（这是主链路，绝对不能接受）

### 三种解法

**方案 A：基因法（Gene Sharding）** —— 把 `gid` 的 hash 低位嵌入到 ID 里，使得 `short_uri` 的路由结果 ≡ `gid` 的路由结果。

```java
// 分 16 表 → 需要 4 bit 基因
int gene = (murmur32(gid) & 0x0F);              // 4 bit 基因
long id = (segmentId << 4) | gene;              // 基因塞进 ID 低 4 位
String shortUri = base62Fixed((id * P + K) % N, 7);

// 自定义分片算法：
//   按 short_uri 路由 → 解码得 id → id & 0x0F = 表号
//   按 gid      路由 → murmur32(gid) & 0x0F = 表号
// 两者恒等 ⇒ 两条链路都单分片命中
```

⚠️ **注意两个坑**：(a) 基因位数一旦定死，**扩容表数量就必须重新生成所有短码**，等于不可扩容；(b) 这正是 nageoffer 那个开源项目的标志性做法，照抄会被认出来。

**方案 B：异构索引表（推荐主推）** —— 主表 `t_link` 按 `short_uri` 分片；另建 `t_link_goto(gid, short_uri)` 按 `gid` 分片，创建时**双写**。

```
创建短链：
  1. 写 t_link（按 short_uri 路由）  ← 主链路数据，必须成功
  2. 写 t_link_goto（按 gid 路由）   ← 索引数据，可最终一致

一致性保证：本地消息表（同库事务写 t_link + msg 记录）+ 定时补偿投递
           或 RocketMQ 事务消息
```

管理链路变成两步：先按 `gid` 查 `t_link_goto` 拿到 `short_uri` 列表（单分片），再按 `short_uri` 批量回查 `t_link`（`IN` 查询，命中少数分片）。

**为什么推荐 B**：
1. 这是**电商订单表的经典做法**（买家维度 + 卖家维度双写），通用性远高于基因法，迁移到别的面试题也能用
2. 它天然引出「本地消息表 vs 事务消息 vs 最大努力通知」这一整套分布式一致性讨论——**这里才是缓存一致性八股的正确落点**（见 3.1）
3. 可扩容（重建索引表即可）
4. 避开了和开源项目撞车

**最强讲法：主推 B，但把 A 完整调研并写进 ADR，面试时主动对比。**
> "我最后选了异构索引表。基因法的优点是不需要双写、没有一致性问题；但它把分片数固化在了短码里，一旦要扩容就得重新生成所有历史短码，而历史短码可能已经印在海报和二维码上了，改不了。异构索引表多了一次查询和一套双写补偿，换来的是可扩容。对我这个场景，可扩容更重要。"

**分片数建议**：`t_link` 分 **2 库 × 8 表 = 16 分片**。这个规模足够展示问题，又不至于让本地环境跑不起来。用 ShardingSphere-JDBC（5.x 的 JDBC 驱动模式，`jdbc:shardingsphere:` + YAML 配置）。

**验收标准**：打开 ShardingSphere 的 SQL 日志，跳转和列表查询都**不能出现广播查询**（不能出现 16 条 SQL）。

## 2.6 ⚠️ 深度不足三：301/302 —— 你只说了"取舍"，实际能讲的远不止

### 基础对比（这层大家都会）

| | 301 永久 | 302 临时 |
|---|---|---|
| 浏览器缓存 | 强缓存，后续**不回源** | 每次回源 |
| 服务器压力 | 小 | 大 |
| 访问统计 | ❌ 丢失大部分 | ✅ 完整 |
| 目标可变更 | ❌ 已缓存的用户改不掉 | ✅ |
| **风控封禁** | ❌ **已缓存的用户拦不住** | ✅ 立即生效 |
| SEO 权重 | 传递给目标 | 不传递 |

### 你需要多讲出来的 5 层

**(1) 决定性理由是风控，不是压力。** 选 302 的真正原因不是"要统计"，而是「**短链被举报为钓鱼后必须能立即断掉；用 301 的话，已经缓存过的浏览器你永远拦不住**」。把风控放在服务器压力之上，这个优先级判断本身就是加分。

**(2) 商业平台的真实做法：`301 + Cache-Control` 组合拳。**
```http
HTTP/1.1 301 Moved Permanently
Location: https://target.example.com/campaign
Cache-Control: private, max-age=90
```
既拿到 301 的减压效果，又把缓存窗口压到 90 秒，风控最多 90 秒生效。**知道这个组合，说明你看过真实响应头，不是背的。**

**(3) 307/308 的存在意义**：301/302 在历史实现中会把 POST 降级成 GET 并丢弃 body；307/308 严格保留请求方法和 body。短链 99% 是 GET，所以 302 够用；**但如果短链要用在 API 回调 / Webhook 上，307 才是正确答案**。

**(4) 绝对不要用 HTML meta refresh 或 JS `location.href` 跳转**：多一个完整 RT + 页面渲染（延迟从 ~10ms 变成 ~300ms）、SEO 差、部分爬虫和 App 内嵌 WebView 不跟随。

**(5) 跳转链路要"瘦"**：跳转是 QPS 最高的接口，不应该走 Spring Security 过滤器链、Session、CSRF、参数校验、事务切面。做法是把跳转 Controller 从过滤器链里排除，或者干脆用一个独立轻量入口。**"我给跳转接口专门做了一条不经过安全过滤器链的路径，压测后 QPS 提升 X%"是一个很实的优化点。**

# Part 3 · 2 个"方案与场景不匹配"（讲出来会被识破是硬套八股）

## 3.1 🟠 缓存一致性：**在短链核心链路上是伪需求**

你写「Cache Aside、延迟双删、还是 Canal 监听 binlog」。这套八股本身没错，但**用在了不存在这个问题的地方**。

**短码 → 长链的映射是近乎不可变的（immutable）。创建之后基本不会改。**

面试对话会变成这样：
> 面试官："你的短链映射会修改吗？"
> 你："基本不会。"
> 面试官："那你的延迟双删在解决什么问题？"
> 你：（卡住）

一旦被这么问一次，面试官对你整个项目的评价就是"背的"。

### 修正：把一致性问题落在**真实存在**的三处

**(a) 短链禁用/下架（硬需求，有时效 SLA）** —— 用户删除、举报下架、风控封禁。要求**秒级生效**，而且必须清掉**多级**缓存（本地 Caffeine + Redis）。

这里才是真正的技术含量：
- Redis 好清（`DEL`），**本地缓存怎么清？** → Redis Pub/Sub 广播失效事件，或 MQ 广播（更可靠），或本地缓存设 3-5s 短 TTL 容忍窗口
- 广播消息丢了怎么办？→ 短 TTL 兜底（这是"广播 + 短 TTL"双保险的设计理由）
- **量化这个代价**："本地缓存 TTL 5s 意味着封禁最多 5 秒后生效。我评估过：对钓鱼链接，5 秒内多放过的点击量在可接受范围；如果业务要求 0 延迟，就得放弃本地缓存，代价是 QPS 从 3.8w 掉到 1.2w。我选了 5s。"
  **这种"把一致性和性能的取舍量化成数字"的表达，是区分'做过'和'背过'的分水岭。**

**(b) 短链目标地址变更（真实业务需求）** —— 企业营销场景：活动页换域名、A/B 分流比例调整、活动结束后改跳到新活动。**这里才需要 Cache Aside + 延迟双删/先更新 DB 再删缓存。** 有了这个业务场景做支撑，你讲延迟双删就是"业务驱动的技术选型"，而不是硬套。

**(c) 访问计数的最终一致** —— Redis 计数 → 批量落库，怎么保证不丢不重（见 4.5）。

**(d) Canal 监听 binlog：只讲，不做。** 5 周时间部署 Canal 是纯浪费。面试时说清取舍就够：
> "我调研过 Canal 订阅 binlog 来刷缓存。它的优点是业务代码零侵入、天然解决双写不一致；缺点是引入了 Canal + MQ 的运维复杂度，而且缓存更新有 binlog 延迟。我这个场景的变更频率极低（禁用/改目标是低频操作），用 Pub/Sub 广播 + 短 TTL 已经够了，多引入一个中间件不划算。数据量再上一个量级、或者有多个下游都要感知变更时，Canal 才值得。"

## 3.2 🟠 你完全没有"读写比"的意识，这导致架构重心偏了

短链系统的核心数字：**读:写 ≈ 100:1 ~ 1000:1**。

这一个数字决定了：
1. MQ 该用在统计而不是创建（2.3）
2. 优化投入的 95% 应该在跳转链路
3. 跳转链路的数据不可变 ⇒ **缓存可以设超长 TTL 甚至永不过期** ⇒ **DB 挂了跳转链路仍能服务**（这是一个非常漂亮的架构优势，见 4.6）
4. 创建链路可以"重"（同步落库 + 同步写缓存 + 同步写 BF + 幂等校验都做完再返回），跳转链路必须"瘦"到极致

**面试时主动抛出这个比例，是你展示"架构思维"最快的方式**：
> "我做的第一件事是估读写比。短链是典型的读多写少，我按营销场景估了 1:500——一条链接生成后平均被点击 500 次。这个比例决定了我 95% 的优化投入都在跳转链路上，创建链路我反而故意做重了：同步落库、同步预热缓存、同步写布隆过滤器，用创建时的几毫秒换跳转时的确定性。"

# Part 4 · 6 个你完全没提、但面试官一定会问的东西

## 4.1 🔥 热点短链（单 Key 热点）—— **这是"高并发读"的真正终局，也是你标题里"高并发"最该有的东西**

场景：某个短链突然爆火（明星发微博、双十一主会场、突发新闻）。

问题：
- Redis Cluster 下，单个 key 只落在**一个** slot / 一个节点 → **单节点被打满，横向扩容 Redis 完全无效**
- 这是"缓存击穿"之外的独立问题，而且更难

三层解法（按顺序讲）：

**(1) 多级缓存：Caffeine (L1) + Redis (L2) + MySQL (L3)**
```java
// 跳转链路
String url = caffeine.getIfPresent(shortUri);           // ~100ns，无网络
if (url == null) {
    url = redis.get(shortUri);                          // ~0.5ms，1 次 RT
    if (url != null) caffeine.put(shortUri, url);
    else { /* BF 判断 → 分布式锁 → 查 DB → 回写 */ }
}
```
Caffeine 配置：`maximumSize(10_000).expireAfterWrite(5, SECONDS)`。
**L1 命中就完全不走网络，这是 QPS 提升一个数量级的关键。**

**(2) 热点探测（动态提升）** —— 不是所有 key 都值得进本地缓存（内存有限）。
- 简单做法：`ConcurrentHashMap<String, LongAdder>` 滑动窗口计数，定时（比如 1s）取 Top-N，超过阈值的 key 提升到本地缓存并延长 TTL
- Caffeine 自带 **Frequency Sketch**（Count-Min Sketch 变体）做 W-TinyLFU 淘汰，本身就有热点倾向性
- 生产级方案：JD hotkey、阿里 Sentinel 热点参数限流

**(3) Key 打散（Redis Cluster 场景）** —— 热点 key 复制 N 份 `link:{uri}:0..9`，读时随机选一份 → 打散到不同 slot。代价是写时要写 N 份、一致性更难。

**(4) 讲清代价** —— 本地缓存的代价就是 3.1(a) 说的：封禁生效延迟。**把"我加了本地缓存"和"我知道它让封禁延迟了 5 秒，并且我评估过这个代价"说在一起，才是完整的。**

## 4.2 🔥 压测数据 —— **简历上"高并发"三个字的唯一凭证**

**这是学生项目最容易被一句话击穿的地方。** 面试官："你这个多少 QPS？怎么压的？瓶颈在哪？"——答不上来，前面所有技术点都作废。

### 压测怎么做才算"真压过"

**(1) 工具**：`wrk`（压跳转链路首选，单机能打出几万 QPS）；`JMeter`（有 UI 好出报告，但自身开销大）；`Gatling`（介于两者之间）。**建议 wrk 出数据 + JMeter 出报告图。**

**(2) 环境必须写清楚**（不写清楚的数字等于没有）：
```
被压机：4C8G（Docker limit），MySQL 8.0 / Redis 7 独立容器
压测机：与被压机分离（同机压测的数字没有意义）
数据量：预置 1000 万条短链
```

**(3) 🔥 请求分布必须用 Zipf，不能用均匀随机。**
这是一个能让面试官立刻信你的细节：
> "我一开始用均匀随机的短码压测，缓存命中率只有 12%，QPS 上不去。后来意识到真实流量是长尾的——少数热门链接占绝大部分点击。我改成 Zipf 分布（α=1.0）之后命中率 99.6%，这才是接近生产的数字。**用均匀随机压缓存系统，会系统性低估缓存效果，等于在测一个不存在的场景。**"

**(4) 必须有逐步优化的对比表**（这张表就是你简历上那几个数字的来源）：

| 阶段 | QPS | P99 | 缓存命中率 | 瓶颈 |
|---|---|---|---|---|
| ① 裸 MySQL | ~1.1k | 86ms | - | DB 连接 + 磁盘 IO |
| ② + Redis | ~1.2w | 12ms | 96% | 网络 RT + 序列化 |
| ③ + Caffeine L1 | ~3.2w | 6ms | 99.6% | Tomcat 线程 + 日志 |
| ④ + 连接池/线程池调优 | ~3.6w | 5ms | 99.6% | 同步日志刷盘 |
| ⑤ + 日志异步 Appender | ~3.8w | 4ms | 99.6% | CPU 饱和 |

（**以上是量级示例，你必须压出自己的真数字。** 4C8G 单机跳转链路做到 2-5 万 QPS 是合理量级。）

**(5) 瓶颈分析：用 `async-profiler` 抓火焰图。**
```bash
./profiler.sh -d 30 -f flame.html <pid>
```
或用 `arthas` 的 `profiler` 命令。

**这一步会给你至少一个"真实发现"，而真实发现比任何八股都值钱。** 最常见的三个：
- **同步日志打印**（Logback 默认同步 + 每次跳转打一行 INFO）→ 改 `AsyncAppender` / 关掉跳转链路的 INFO 日志 → 常见提升 15-30%
- **JSON 序列化**（跳转链路存 JSON 对象而不是纯字符串）→ 直接存 `origin_url` 字符串，省掉反序列化
- **`Tomcat maxThreads` / HikariCP `maximumPoolSize` 默认值不匹配** → 压测调参

**(6) 简历上写真数字。** ❌ 不要写"支撑百万 QPS"——4C8G 单机做不到，会被当场问穿。✅ 写"4C8G 单机跳转 QPS 从 1.1k 提升至 3.8w，P99 从 86ms 降至 4ms"——**这个数字更小，但可信度是前者的一百倍。**

## 4.3 幂等：同一长链重复创建，返回同一短码还是新短码？

**这是一道"考你有没有产品思维"的题，而且没有唯一正确答案——能说清"取决于业务语义"才是满分。**

- **bit.ly 的行为**：同一账号 + 同一长链 → 返回同一短码
- **但营销场景恰恰相反**：同一个落地页要生成 20 个不同短码，分别投放到微信/微博/抖音/短信，用于**渠道归因**。这时"幂等"是错的。

**正确答案**：默认按 `(gid, url_hash)` 幂等，但提供 `forceNew=true` 参数支持渠道归因场景。

实现要点：
```sql
url_hash BINARY(16) NOT NULL COMMENT 'MD5(origin_url)'
UNIQUE KEY uk_gid_url (gid, url_hash)
```
⚠️ **为什么不直接给 `origin_url` 建唯一索引**：`VARCHAR(2048)` utf8mb4 = 8192 字节，超过 InnoDB 索引 3072 字节上限，建不了。所以必须用定长 hash。**这是个真实的工程细节，答出来加分。**

⚠️ **分库分表下的坑（深挖点）**：唯一索引只在**单个分片内**生效！`t_link` 按 `short_uri` 分片，而幂等判断按 `url_hash` —— 同一个长链两次创建会拿到不同的 `short_uri`，落到不同分片，唯一索引拦不住。
解法：
- 单独的去重表按 `url_hash` 分片（本质又是一张异构索引表）
- 或 Redis `SETNX url_hash → short_uri`（快但要处理 Redis 挂了的情况）
- 或直接把幂等做成"最佳努力"（承认极端并发下可能生成两个短码，业务上可接受）

**接口层幂等**（防重复提交）：`requestId` + Redis `SET NX EX`。

## 4.4 过期与回收：**短码不应该回收**（这个结论要能自己推出来）

- Redis TTL 必须 ≤ DB 的 `valid_end`（否则短链过期了缓存还在跳）
- 过期/删除用**逻辑删除** `del_flag`，不物理删除（要保留统计数据）
- 过期短链访问 → 返回失效落地页（HTTP `410 Gone` 或 200 + 提示页），**不要 302 到首页**（用户会困惑）

**🔥 短码要不要回收复用？答案是不要，理由有三层：**
1. **业务事故风险**：老的二维码、海报、短信、印刷品上还印着这个短码。复用后老海报会跳到别人的活动页 —— 这是真实的线上事故
2. **布隆过滤器不能删位**，复用会让 BF 的语义混乱
3. **根本不需要**：62^6 = 568 亿，按 1 亿/年用 568 年

**能从"BF 不支持删除"这个技术约束，反推出"短码不回收"这个产品决策，并且用容量数字证明这个决策没有代价——这个推理链条本身就是很好的面试素材。**

**冷热分离**（可选，有时间再做）：一年前的短链访问量极低 → 归档到历史表，主表只留热数据。

## 4.5 访问统计：你提了但完全没深挖，而这里能挖出很多

```
跳转链路 → 投 MQ（异步，绝不阻塞）→ 消费端 → Redis 计数 → 定时批量落库
```

**(1) 统计绝不能影响跳转。** MQ 发送失败怎么办？→ 降级为本地内存队列暂存 / 落本地磁盘文件，后台补投。**"统计丢一点可以，跳转挂了不行"这个优先级要主动说出来。**

**(2) PV：Redis `INCR`。** 落库时用 Redis `Pipeline` 批量取 + MySQL 批量 upsert：
```sql
INSERT INTO t_link_stats_daily (short_uri, stat_date, hour, pv, uv)
VALUES (?,?,?,?,?)
ON DUPLICATE KEY UPDATE pv = pv + VALUES(pv), uv = VALUES(uv);
```

**(3) UV 去重：HyperLogLog。**
- `PFADD` / `PFCOUNT`，标准误差 **0.81%**，dense 编码固定 **12KB**
- 🔥 **深挖点**：Redis HLL 有 **sparse / dense 两种编码**，低基数时用 sparse 只占几十字节，由 `hll-sparse-max-bytes`（默认 3000）控制切换。所以"每个短链每天一个 HLL"不会真的爆内存——冷链接的 HLL 只有几十字节。**知道这个，说明你真读过 Redis 的行为而不是只会背"HLL 占 12KB"。**
- 精确 UV 需求（少量重点链接）：用 Redis `Set` 或 `Bitmap`（用户 ID 连续时 Bitmap 极省）

**(4) 多维统计**：
- 地域：`ip2region`（离线库，无网络调用，几 MB 内存，微秒级）
- 设备/OS/浏览器：解析 `User-Agent`（`yauaa` 或 `UserAgentUtils`）
- 来源：`Referer`
- 时段：按小时打点

**(5) 消费端幂等**：MQ 至少一次投递 → 重复消费会导致 PV 虚高。用 `messageId` + Redis `SETNX`（TTL 几分钟）去重。**不过统计场景可以说"我这里选择容忍少量重复，因为幂等去重本身的成本高于误差收益"——能主动做这个取舍判断很好。**

**(6) 重试 + 死信队列**：消费失败重试 3 次 → 进死信队列 → 告警 + 人工/定时补偿。

**(7) 验收标准**：压测发了 100 万次请求，统计出来的 PV 误差应 < 1%。**能报出这个误差数字，等于证明你真的对过账。**

## 4.6 稳定性：故障降级矩阵（大厂校招会问）

| 故障 | 影响 | 降级方案 |
|---|---|---|
| **Redis 挂** | 跳转全部落 DB → DB 瞬间被打死 | ① Caffeine L1 兜住热点（这是本地缓存的第二个价值）② Sentinel/信号量限制到 DB 的并发（比如最多 50）③ 超出直接返回错误页，**保护 DB 比服务全部请求更重要** |
| **MySQL 挂** | 创建不可用 | 🔥 **跳转链路仍可服务** —— 因为短链数据不可变，缓存可以设超长 TTL / 永不过期。这是短链架构的一个真实优势，**主动讲出来很亮** |
| **MQ 挂** | 统计中断 | 本地暂存 + 后台补投；**跳转链路完全不受影响** |
| **单短链热点** | Redis 单节点打满 | 见 4.1 |
| **恶意刷跳转** | 统计污染 + 带宽 | 限流（IP + 短码维度）+ UA/频率识别 |

**⚠️ 这一项必须真做一次演练**（`docker stop redis` 然后压测，截图记录 QPS 和错误率变化）。**"我把 Redis 停了压测，QPS 从 3.8w 降到 1.4w，错误率 0%，因为本地缓存兜住了热点"—— 这句话有数据支撑，杀伤力极大。**

## 4.7 安全：开放重定向与钓鱼风控（差异化加分项，几乎没人做）

**短链本质就是一个 Open Redirect，这是它的头号真实业务风险。**

- **钓鱼防护**：目标域名黑白名单、风险中间页（"你即将离开本站前往 xxx.com，确认继续？"）、接入 URL 信誉库
- **🔥 SSRF**：如果你做了"抓取目标页 title / favicon 做预览"这个功能（很多短链平台有），就引入了 SSRF —— 攻击者创建一个指向 `http://127.0.0.1:8080/admin` 或云元数据地址 `http://169.254.169.254/latest/meta-data/` 的短链，你的服务器会替他去请求内网。
  防护：解析后的 IP 必须校验（拒绝私有网段 `10./172.16./192.168./127./169.254.`），并防 **DNS Rebinding**（校验时和请求时解析出的 IP 可能不同 → 必须"解析一次 IP，然后直连这个 IP"）。
  **在短链项目里讲 SSRF，面试官会印象非常深——因为几乎没人想到。**
- **创建接口刷量**：账号维度 + IP 维度限流、验证码
- **短码枚举**：见 2.2

**限流具体实现**（别停在名词上）：
- Redis + Lua 令牌桶（Lua 保证原子性，这是选 Lua 而不是多条命令的理由）
- 或 Sentinel（注意：spring-cloud-alibaba 对 Spring Boot 版本敏感，见 5.2）
- **两个接口策略必须不同**：创建接口按 `userId` 严格限流（如 10 QPS）；跳转接口按 `IP + shortUri` 宽松限流（如 100 QPS），因为正常用户可能高频访问

## 5.2 技术栈：**留在 Spring Boot 4.0.7，但必须换掉 RocketMQ，并在第 1 天验证 ShardingSphere**

> ⚠️ **这一节我改过一次。** 我最初判断是"降级到 Spring Boot 3.5.x 保稳"，但去核实版本现状后发现这个建议站不住，理由见下。**把这个纠错过程留在这里，也是想说明一件事：技术选型必须去查当下的真实版本状态，凭"历史上生态跟进慢"的印象做决策是会错的。这个习惯本身就是面试官在找的东西。**

你现在的 `pom.xml` 是 **Spring Boot 4.0.7 + Java 21 + `spring-boot-starter-webmvc`**。Spring Boot 4.0.0 于 2025-11-20 GA（基于 2025-11-13 GA 的 Spring Framework 7）；4.0.7 发布于 2026-06-10，同日 **4.1.0** 也已 GA。

### 逐组件核实结果（2026 年 7 月现状）

| 组件 | Spring Boot 4 支持情况 | 风险 |
|---|---|---|
| **MyBatis-Plus** | ✅ `com.baomidou:mybatis-plus-spring-boot4-starter` 自 **3.5.13**（2025-08）起提供；最新 **3.5.17**（2026-07-08）的 POM 直接引入 `spring-boot-dependencies:4.0.1` | 🟢 低。**你写的坐标是对的** |
| **Redisson** | ✅ `redisson-4.0.0` 明确支持 "Spring Boot 4.0 integration"；最新 starter **4.5.0** 对齐 Boot 4.0.6 | 🟢 低 |

我原来的降级建议错在一个关键事实上：**Spring Boot 3.5.x 的 OSS 支持已于 2026-06-30 结束**（末版 3.5.16）。降级等于迁到一条已停止维护的线上；4.0.x 支持到 2026-12-31，4.1.x 到 2027-07-31。**降级不但没解决问题，还把你放到了 EOL 分支上。**

三条原本"必须降级"的理由，两条已被推翻（MyBatis-Plus、Sentinel 都已支持 Boot 4）。唯一真实的短板是 RocketMQ，而**这本来就是个单点问题，换 MQ 比整套降级便宜得多**。

### 你要做的两件具体事

**(1) MQ 选 RabbitMQ，不选 RocketMQ**（这条建议不变，但现在理由更硬了）

- **RabbitMQ**（推荐）：`spring-boot-starter-amqp` 由 Spring 官方维护，与 Boot 版本同步发布，不存在滞后；Docker 一行起；能讲死信队列 / 延迟队列 / publisher-confirm / 手动 ack。**时间成本最低，兼容风险为零。**
- **Kafka**（次选）：统计日志场景最对味（高吞吐、分区、消费组），`spring-kafka` 也是官方维护
- **RocketMQ**（排除）：starter 卡在 Boot 2.7 基线。如果你就是想讲它，用"我调研过但没选"的方式——**而且现在你的理由是可核实的事实，不是感觉**：
  > "我本来想用 RocketMQ 讲事务消息，查了一下它的 spring-boot-starter 到 2.3.6 还是 Spring Boot 2.7 / Java 8 基线，跟我的 Boot 4 对不上。可选项是自己包一层原生 `rocketmq-client`，但那是纯适配工作、没有技术含量。所以我换了 RabbitMQ。"

  **❗只选一个 MQ。两个 MQ 在 5 周里是自杀。**

**(2) 🔴 Day 1 就冒烟验证 ShardingSphere，不要等到第 4 周**

这是整个方案里**唯一的高风险未知项**。Jackson 2 / Jackson 3 冲突如果爆掉，你在第 4 周才发现就来不及了。

```
Day 1 花 2 小时做这件事：
  1. 建一个最小工程：Boot 4.0.7 + ShardingSphere-JDBC 5.5.3 驱动模式 + 一张分 2 表的表
  2. 跑通 insert + select
  3. 跑通了 → 按原计划第 4 周做分库分表
     跑不通 → 立刻走 Plan B，不要在这上面耗超过半天
```

**Plan B（如果 ShardingSphere 在 Boot 4 下跑不通）**，按优先级：
1. **手写分片路由**：一个 `ShardingRouter` 工具类算出 `tableSuffix = hash % 16`，配合 MyBatis-Plus 的 `DynamicTableNameInnerInterceptor` 动态改表名。**代码量约 100 行，而且面试价值更高**——因为你能讲清分片路由的内部机制，而不只是"我配了个中间件"。
2. 用 `dynamic-datasource-spring-boot4-starter`（baomidou 自家，跟 MyBatis-Plus 同步维护）做多数据源，分表自己路由
3. 单库分表（只分 16 表不分库），完全手写路由，最简单

**说实话：Plan B 的第 1 条在面试里比 ShardingSphere 更能加分。** "我手写了分片路由"比"我配置了 ShardingSphere 的 YAML"深度高一个档次——因为后者面试官会追问"它内部怎么改写 SQL 的"，前者你就是答案本身。

## 5.3 表结构（可直接用）

```sql
-- ═══════════ 短链主表（ShardingSphere：short_uri 分 2库 × 8表）═══════════
```

**这张表里有 4 个能当面试题的设计决策**：
1. **🔥 主键为什么用 `id`（发号器）而不是 `short_uri`？** —— InnoDB 主键是聚簇索引。`short_uri` 是**随机字符串**（不管是随机生成还是 Feistel 加密而来），用它做主键 = 随机位置插入 = **页分裂严重 + 写放大 + 索引碎片**。发号器 ID 趋势递增，顺序追加写，几乎不分裂。**这是一道经典的 InnoDB 题，你的表结构天然带着它。**
2. **为什么不用 `AUTO_INCREMENT`？** —— 分库分表下多个分片的自增会冲突。所以必须外部发号。
3. **为什么幂等索引建在 `url_hash BINARY(16)` 而不是 `origin_url`？** —— `VARCHAR(2048)` utf8mb4 = 8192 字节 > InnoDB 索引键 3072 字节上限，建不了索引。`BINARY(16)` 定长 16 字节，且比 `CHAR(32)` 存十六进制字符串省一半。
4. **`del_flag` 逻辑删除**，因为要保留历史统计数据。

## 5.4 号段发号器（这是你的第一个深挖点，要做到"能讲 5 分钟"）

**核心要素（缺一个就不完整）**：

```java
@Component
public class SegmentIdGenerator {
    // 双 Buffer：current 消耗到阈值时后台异步加载 next，切换时零等待
    private volatile Buffer current;
    private volatile Buffer next;
    private static final double LOAD_FACTOR = 0.2;   // 剩 20% 时预加载

    public long nextId() {
        long id = current.cursor.getAndIncrement();
        if (id > current.max) {              // 当前段耗尽 → 切换
            switchBuffer();
            return nextId();
        }
        if (current.remainRatio() < LOAD_FACTOR && !next.ready) {
            asyncLoadNext();                 // 后台线程去 DB 取下一段，不阻塞调用方
        }
        return id;
    }
}
```

**DB 取号用乐观锁 CAS（不要用 `SELECT ... FOR UPDATE`）**：
```sql
UPDATE t_id_segment
   SET max_id = max_id + step, version = version + 1
 WHERE biz_tag = 'short_link' AND version = #{version};
-- 影响行数 = 0 → 有并发，重试（带退避，最多 3 次）
```

**能讲的深度点（按重要度）**：

1. **为什么用双 Buffer**：单 Buffer 在段耗尽的瞬间，所有请求都会阻塞等 DB 返回（一次 DB RT ≈ 1-5ms，此刻 P99 会有尖刺）。双 Buffer 提前异步加载，**消除了这个毛刺**。压测时能看到：单 Buffer 的 P999 有周期性尖峰，双 Buffer 平滑。**这个观察值千金。**
2. **step 怎么定 / 动态调整**：step 太小 → DB 压力大；太大 → 服务重启丢号多。美团 Leaf 的做法是**根据上一个段的消耗时长动态调整**（消耗 < 15min 则 step ×2，> 30min 则 step ÷2）。
3. **重启丢号**：内存里未用完的号段会丢。**这在短链场景完全可接受**（短码空间 568 亿，丢几千个号无所谓）。但如果是订单号，丢号会导致对账问题——**能区分"哪些业务能容忍丢号"是加分项**。
4. **为什么乐观锁而不是悲观锁**：`FOR UPDATE` 会持有行锁直到事务提交，取号是高频操作，行锁竞争会成为瓶颈。乐观锁失败重试的成本更低（且取号本身冲突概率不高，因为有本地 buffer 削掉了 99.9% 的 DB 访问）。
5. **单点问题**：DB 挂了取不到号 → 内存 buffer 能撑一段时间（step=1000 时约撑 1000 次创建）；更强的做法是双 DB 或降级到本地雪花（**牺牲短码长度换可用性**——这个取舍很漂亮）。
6. **发号器 ID 的用途要说清**：本方案里 ID 用作 `t_link` 主键（趋势递增，避免页分裂），短码另走随机+判重路径（抗枚举）。**"我把'唯一性'和'不可猜测性'解耦成两套机制"是一个很清晰的架构表达。**

**必须写的单测（这是"我真的验证过"的证据）**：

## 5.5 跳转链路（第二个深挖点：高并发读）

完整防护链（**顺序有讲究，要能解释每一步为什么在这个位置**）：

```
1. Caffeine L1        （最快，先查；命中就完全不走网络）
2. Redis L2           （分布式共享）
3. BloomFilter        （拦"从来不存在"的短码 → 防穿透；放在查 DB 前）
4. 空值缓存           （拦"BF 假阳性 + 曾存在但已删除"的短码；TTL 短，2-5min）
5. Redisson 分布式锁  （防击穿：热点 key 过期瞬间只放 1 个请求进 DB）
6. 双重检查           （拿到锁后再查一次缓存 —— 前面等锁的请求可能已经回写了）
7. MySQL              （最后一道）
8. 回写 L2 + L1       （不存在也要写空值缓存）
```

**关键：为什么需要"空值缓存 + 布隆过滤器"两个？**（高频击穿题）
- BF 有**假阳性**：判断"可能存在"的短码里有一部分其实不存在 → 这部分会穿透到 DB → 需要空值缓存兜住
- BF 不支持删除：已删除的短链在 BF 里还是"存在" → 也需要空值缓存
- 反过来，光有空值缓存不够：攻击者构造**海量不同的**随机短码，每个都会先查一次 DB 才能建立空值缓存，DB 还是会被打穿 → 需要 BF 在前面挡住
- **两者是互补的：BF 挡掉绝大多数（99.99%）不存在的请求，空值缓存兜住漏过来的那部分。**

**跳转要"瘦"**（见 2.6-(5)）：不走 Security 过滤器链、不开事务、不打同步 INFO 日志。

## 5.6 缓存失效广播（对应 3.1-a）

```java
// 禁用/封禁短链时
public void disable(String shortUri) {
    db.updateEnableStatus(shortUri, DISABLED);       // 1. 改 DB
    redis.delete(KEY_PREFIX + shortUri);             // 2. 清 Redis
    redis.convertAndSend("cache:invalidate", shortUri); // 3. Pub/Sub 广播清本地
}

@Component
class LocalCacheInvalidateListener implements MessageListener {
    public void onMessage(Message msg, byte[] pattern) {
        caffeine.invalidate(deserialize(msg));       // 各实例清自己的 L1
    }
}
```

**必须讲清的兜底**：Pub/Sub 是 **fire-and-forget，不保证送达**（实例正好在重连时会漏消息）。所以 **Caffeine 必须同时设 5s 短 TTL 作为第二层保险**。
> "广播是为了让 99% 的情况下 100ms 内生效，短 TTL 是为了保证最坏情况下 5 秒必定生效。两层保险各解决一半问题。"

**更强的做法**（讲取舍）：用 MQ 广播模式（RabbitMQ fanout / RocketMQ BROADCASTING）替代 Pub/Sub，能持久化和重试。代价是延迟略高、复杂度上升。

在 README 里放一份 `docs/adr.md`，记录 8-10 个关键决策：

```markdown
## ADR-003 短码生成与编码方案

**背景**：需要生成全局唯一、尽可能短（目标 6 位）、且不可被顺序枚举的短码。

**考虑过的方案**
| 方案 | 短码位数 | 唯一性 | 抗枚举 | 结论 |
|---|---|---|---|---|
| UUID | 22 位 | 天然 | 强 | ❌ 太长 |
| 雪花算法 | 10-11 位（随时间增长） | 天然 | 中 | ❌ 太长；根因是时间戳位让 ID 空间稀疏 |
| 号段 → Base62 直接编码 | **6 位** | 天然 | ❌ **完全可枚举** | ❌ 安全不可接受 |
| 号段 → 模乘置换 → Base62 | **6 位** | 天然（双射） | ⚠️ 混淆级 | ❌ **连续两次调用创建接口即可反解出 P**（差值恒为 P），只能防路人 |
| 号段 → Feistel FPE → Base62 | **6 位** | 天然（双射） | ✅ 密钥级 | ⭕ 备选，需 cycle-walking 处理 2^36 > 62^6 的越界 |
| **随机 6 位 Base62 + BF 判重 + 唯一索引兜底** | **6 位** | 靠判重 | ✅ 强 | ✅ **采用** |

**决策**：`SecureRandom` 生成 6 位 Base62 → 布隆过滤器判重 → 唯一索引兜底并发竞态，最多重试 5 次。号段发号器保留，用于 `t_link` 主键（趋势递增，避免 InnoDB 页分裂）。

**为什么不选 Feistel**：Feistel 是更"优雅"的答案（双射、无需判重、可逆），但随机+判重在本场景的碰撞概率仅 0.018%（1000 万数据 / 568 亿空间），实现量是它的 1/4，而且让布隆过滤器的"判重"用途变成真正必要的，整体设计更自洽。若未来需要从短码反解 ID（例如改用基因法分片），再切 Feistel。

**放弃了什么**：失去了短码 → ID 的可逆性（因此分片选异构索引表而非基因法，见 ADR-005）；每次生成多一次 BF 查询；号段模式重启会丢未用完的号（本场景可接受）。
```

**这份文档本身就是面试素材**，而且它是你"这个项目是我自己想的"最有力的证据——因为它记录了你**放弃过什么**，而抄项目的人没有放弃过任何东西。

## 五条写法原则

1. **每条都是「问题 → 方案 → 取舍 → 数据」**，不是「我用了 X」
2. **数字必须是自己压出来的**，且能随时说清压测环境（4C8G、压测机分离、Zipf 分布、1000 万数据量）
3. **敢写"我否决了 X 方案，因为 Y"** —— 这是最能体现深度的句式，也是最难伪造的
4. **敢写"我踩了坑并找到根因"**（雪花→11位、同步日志瓶颈）—— 真实感的最大来源
5. **长度 6-8 条，占简历约 1/3 页**。超了就砍掉最弱的那条

# Part 8 · 30 道高频击穿题（附答法要点）

> 这些题的特点：**背项目的人答不上来，真做过的人张口就来。** 面试官就是靠它们筛人的。

## 短码生成（6 题）

1. **你的短码几位？为什么是这个位数？** → 6 位；62^6 = 568 亿；按 1 亿/年够 568 年。
2. **🔥 用雪花算法生成的 ID 转成 Base62 是几位？** → 11 位（`ceil(63/log2(62))`）。所以雪花不适合，根因是时间戳位让 ID 空间稀疏。
3. **号段模式服务重启会丢号吗？可以接受吗？** → 会丢内存里未用完的段。短链可接受（空间大）；订单号不行（对账）。
4. **为什么用乐观锁而不是 `SELECT FOR UPDATE`？** → 行锁持有到事务提交，取号高频会成瓶颈；且本地 buffer 已削掉 99.9% 的 DB 访问，冲突概率低。
5. **step 怎么定？太大太小分别什么问题？** → 太小 DB 压力大；太大重启丢号多。Leaf 的做法是按上段消耗时长动态调整（<15min 翻倍，>30min 减半）。
6. **🔥 号段是递增的，短码会不会被爬虫顺序遍历？** → 会，这是真实安全风险（bit.ly / goo.gl 早年被批量爬出私密分享链）。按 4 级阶梯答：①打乱字符表 = 单表替换密码，无效；②模乘置换 `(id·P+K) mod 62^6` 是双射且可逆，但**连续两次调用创建接口，两个密文之差恒为 P，两次 API 调用就能反解**，只算混淆不算安全；③Feistel FPE（4 轮 + HMAC 轮函数 + cycle-walking 处理 2^36 > 62^6 越界）才是密钥级安全且保持双射；④我选的是随机 6 位 + BF 判重 + 唯一索引兜底，碰撞率 0.018%，最简单且安全。**把这个阶梯讲完，等于展示了完整的方案评估能力。**

## 缓存（8 题）

7. **穿透、击穿、雪崩分别是什么？你分别怎么防的？** → 穿透=查不存在的数据（BF+空值缓存）；击穿=热点 key 过期（分布式锁+双重检查/逻辑过期）；雪崩=大量 key 同时过期或 Redis 挂（TTL 加随机、多级缓存、限流熔断）。
8. **🔥 有了布隆过滤器为什么还要空值缓存？** → BF 有假阳性；BF 不支持删除（已删短链在 BF 里仍"存在"）。两者互补：BF 挡 99.99%，空值缓存兜住漏过的。
9. **🔥 光有空值缓存不够吗？** → 不够。攻击者构造海量**不同**的随机短码，每个都要先查一次 DB 才能建立空值缓存，DB 仍被打穿。
10. **🔥 新建短链要写布隆过滤器吗？先写 BF 还是先落库？** → 必须写，且**先写 BF**。理由：BF 误差单向（可能误报存在，绝不误报不存在），所以让失败方向与之对齐——BF 多位只是多一次穿透，BF 漏位是合法短链永久 404。
11. **布隆过滤器占多少内存？怎么算的？** → `m/n = -ln(p)/(ln2)²`。1000 万 / 0.01% → 19.2 bit/元素 ≈ 23MB，k=13。
12. **布隆过滤器不支持删除，容量满了怎么办？** → 双 BF 滚动重建（DB 全量构建新 BF 后切流）；或 Counting BF（4-8 倍内存）；或 Cuckoo Filter（支持删除、空间更优，但插入可能失败）。
13. **本地布隆过滤器和 Redis 布隆过滤器怎么选？** → 多实例必须 Redis（否则 A 实例新建的短链被 B 实例拦掉，且重启丢失、内存×实例数）。想优化延迟做两层，要求本地是 Redis 的子集。
14. **🔥 你的短链会修改吗？那你的缓存一致性在解决什么？** → **这题就是专门用来打假的。** 正确答法：短码→长链近乎不可变，所以核心链路上一致性是弱需求。真正需要一致性的是三处：①禁用/封禁（秒级生效，多级缓存都要清）②企业改跳转目标（Cache Aside）③统计计数最终一致。

## 多级缓存 & 热点（4 题）

15. **🔥 加了本地缓存，封禁一个短链要多久生效？** → Pub/Sub 广播 + 5s 短 TTL 双保险：99% 情况 100ms 内，最坏 5s。**并且要量化代价**："如果要求 0 延迟就得放弃本地缓存，QPS 从 3.8w 掉到 1.2w，我选了 5s。"
16. **Pub/Sub 消息丢了怎么办？** → Pub/Sub 是 fire-and-forget 不保证送达，所以必须有短 TTL 兜底。更强的做法用 MQ 广播模式（可持久化重试）。
17. **🔥 某个短链突然爆火，Redis 单节点被打满，横向扩容 Redis 有用吗？** → **没用**，单 key 只落一个 slot。解法：①本地缓存（这是唯一真正的解）②热点探测动态提升 ③key 复制 N 份打散到不同 slot。
18. **热点怎么探测？** → 滑动窗口 `LongAdder` 计数取 Top-N；Caffeine 自带 Frequency Sketch（W-TinyLFU）本身有热点倾向；生产用 JD hotkey / Sentinel 热点参数限流。

## 分库分表（5 题）

19. **🔥 你的分片键是什么？** → `t_link` 按 `short_uri`（跳转是主链路，必须单分片）。
20. **🔥 那"查我创建的所有短链"怎么办？不是要扫所有分片？** → **这是这道题的全部难点。** 三个解法：①基因法（把 gid 的 hash 嵌进短码）②异构索引表 `t_link_goto` 按 gid 分片双写（我选这个）③剥离到 ES。
21. **基因法和异构索引表你为什么选后者？** → 基因法把分片数固化在短码里，扩容要重新生成所有历史短码，而短码可能已经印在海报和二维码上，改不了。异构索引表多了双写和一致性成本，换来可扩容。
22. **双写怎么保证一致？** → 本地消息表（同库事务写主表 + 消息记录，定时补偿投递）；或 RocketMQ 事务消息；或最大努力通知 + 对账任务。
23. **🔥 主键为什么不用 `short_uri`？** → InnoDB 主键是聚簇索引。`short_uri` 是随机字符串 → 随机位置插入 → 页分裂 + 写放大 + 索引碎片。发号器 ID 趋势递增，顺序追加写。**这也是号段发号器在我方案里的真正用途——不是生成短码，是生成主键。**

## 跳转 & HTTP（3 题）

24. **🔥 301 还是 302？为什么？** → 302。**决定性理由不是"要统计"，而是风控**——短链被举报为钓鱼后必须能立即断掉，301 已缓存的浏览器永远拦不住。补充：商业平台常用 `301 + Cache-Control: private, max-age=90` 兼顾两者。
25. **307/308 和 301/302 的区别？** → 307/308 严格保留请求方法和 body（301/302 历史实现会把 POST 降级成 GET）。短链 99% 是 GET 所以 302 够用，但用在 API 回调上必须 307。
26. **跳转接口做过什么优化？** → 不走 Security 过滤器链 / Session / CSRF / 事务切面；不打同步 INFO 日志（火焰图定位到的瓶颈）；缓存里直接存 URL 字符串而不是 JSON 对象（省反序列化）。

## 统计 & MQ（3 题）

27. **🔥 你说用 MQ 异步落库削峰，那用户拿到短码立刻访问怎么办？** → **这题就是打假 MQ 用错地方的。** 正确答法：创建同步落库（读写比 1:500，创建 QPS 本来就低，不需要削峰）；MQ 用在统计链路（那里 QPS = 跳转 QPS）；批量创建走异步任务 + 批量 insert + 轮询进度。
28. **UV 怎么去重？HyperLogLog 占多少内存？** → PFADD/PFCOUNT，误差 0.81%，dense 固定 12KB。**加分**：Redis HLL 有 sparse/dense 两种编码，低基数只占几十字节（`hll-sparse-max-bytes` 控制切换），所以冷链接不会真的占 12KB。
29. **MQ 挂了统计怎么办？会影响跳转吗？** → 绝不影响。发送失败降级本地内存/落盘暂存，后台补投。优先级是"统计丢一点可以，跳转挂了不行"。

## 稳定性 & 安全（4 题）

30. **🔥 Redis 挂了会怎样？** → 全部落 DB，DB 会被打死。三层防护：①Caffeine 兜热点（本地缓存的第二个价值）②限制到 DB 的并发（如 50）③超出直接返回错误页——**保护 DB 优先于服务全部请求**。演练数据：QPS 3.8w→1.4w，错误率 0%。
31. **🔥 MySQL 挂了跳转还能用吗？** → **能，而且这是短链架构的一个真实优势**：数据不可变，缓存可设超长 TTL 甚至永不过期。只有创建链路降级为不可用。
32. **短链会不会被用来做钓鱼？你怎么防？** → 域名黑白名单 + 风险中间页 + URL 信誉库；跳转按 IP+短码限流；这也是选 302 而非 301 的决定性理由（能立即断链）。
33. **🔥 你抓取目标页 title 做预览，有没有 SSRF 风险？** → 有。攻击者创建指向 `127.0.0.1` / `169.254.169.254`（云元数据）的短链，服务器会替他请求内网。防护：校验解析后的 IP（拒绝私有网段）+ 防 DNS Rebinding（解析一次 IP 后直连该 IP，不要二次解析）。**这题很少有人想到，答出来印象极深。**

## 压测（3 题）

34. **你压测怎么做的？环境是什么？** → wrk 压跳转 + JMeter 出报告；压测机与被压机分离；4C8G Docker limit；预置 1000 万数据。
35. **🔥 请求分布用什么？** → **Zipf（α=1.0），不能用均匀随机。** 均匀随机时命中率只有 12%，会系统性低估缓存效果——那是在测一个不存在的场景。改 Zipf 后 99.6%，才接近生产。
36. **瓶颈在哪？怎么找的？** → async-profiler 抓火焰图，发现同步日志刷盘占了大量 CPU，改 AsyncAppender 后 QPS +22%。后续瓶颈是 CPU 饱和。

## 诚信题（1 题，但最重要）

37. **🔥 你这个是不是跟着某个开源项目/课程做的？** → **一定诚实**："我调研过 nageoffer 的 shortlink 项目，参考了它的问题定义。但在三个地方做了不同选择：①短码用随机+布隆判重而不是它的方案，因为我先分析了顺序编码的可枚举风险 ②分片用异构索引表而不是基因法，因为基因法不可扩容 ③MQ 只用在统计链路而不是创建链路，因为异步落库会导致 404。我把这些决策都记在了 ADR 里。" —— **装作不知道，一旦被识破就是诚信崩塌，代价远大于承认参考。**
