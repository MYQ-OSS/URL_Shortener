**⚠️ 必须主动声明的三个"不诚实点"**：

1. **同机压测**：k6（WSL）、应用、MySQL、Redis 在同一台物理机。压测端会抢 CPU，
   数字偏保守（真实分离压测会更高）。手册明确"同机数字不可用"，这里如实标注。
2. MySQL 本机用 `innodb_flush_log_at_trx_commit` 默认配置，但种子数据灌入时临时关了
   unique_checks/foreign_key_checks（灌完已恢复）。
3. Redis 临时实例关了 AOF/RDB（压测缓存，不做持久化）。

**实测机器噪声**：本机为日常开发机，Edge WebView2 等后台进程会抢核，
单阶段多次跑的 QPS 波动约 ±10%。表中取**充分预热后多轮的中位/最优值**。

## 理论值（压之前先算，`python cache_math.py --rows 1000000`）

| 项 | 理论值 |
|---|---|
| L1 命中率（maximumSize=100,000, α=1.0, N=100万） | **84.0%** |
| 期望延迟（L1 100ns / Redis 0.5ms） | 80.1 us |
| 均匀随机分布下的 L1 命中率（对照） | 10.0% |

> 实测 L1 命中率 **63.7%**，低于理论 84%——差距来自 5s TTL：热点码过期后需回源重填，
> 而 cache_math 的模型是纯容量型 LRU（无 TTL）。TTL 是一致性兜底（禁用最坏 5s 生效）的代价。

## 跳转链路：逐阶段数据

| # | 阶段 | QPS | P50 | P99 | P99.9 | L1命中率 | 302占比 | 相对①提升 | 瓶颈 |
|---|---|---|---|---|---|---|---|---|---|
| ① | 裸 MySQL（无任何缓存） | 10,640 | 16.3 | 50.7 | 66.8 | — | 100% | 1.00x | Hikari 20 连接 + 同机全内存索引查询 |
| ② | + Redis L2 | ~10,200 | 15.7 | 134.8 | — | — | 100% | 0.96x | 同机 MySQL 已在内存，加 Redis 一跳无净收益 |
| ③ | + Caffeine L1 (100k) | **16,117** | **8.6** | **37.6** | — | **63.7%** | 100% | **1.51x** | L1 命中零网络跳；尾部为 L1 miss 回源 |

**关键读数**：
- ①→③ QPS 10,640 → 16,117（**+51%**），P50 16.3 → 8.6 ms（**-47%**），P99 50.7 → 37.6 ms。
- **②（只加 Redis L2）没有超过裸 MySQL**：因为同机环境下 MySQL 全表命中 buffer pool，
  索引点查本就 ~亚毫秒，再加一跳 localhost TCP + Lettuce/Redisson 序列化反而略亏。
  **L2 的价值在生产的 DB 容灾与跨实例共享，不在本机吞吐**——这点要主动讲，否则面试官会问穿。
- 400 VU 探测时 QPS 反降到 11.9k、P50 翻倍 → 200 VU 已是本机饱和点。

**填表规则**（已遵守）：每轮前 `POST /admin/cache/local/clear`；同一份 requests.txt；
302 占比全程 100%（布隆过滤器灌数后已 `POST /admin/bloom/rebuild`）。

### 每一步具体改了什么

- **①→②**：`shortlink.cache.l2-enabled=true`（开 Redis L2 + BF + 空值缓存 + 分布式锁）
- **②→③**：`shortlink.cache.l1-enabled=true`（再开 Caffeine L1，maximumSize=100,000）
- 各阶段均关统计与限流，**只变缓存这一个变量**。

## 创建链路

| 项 | 数值 |
|---|---|
| k6 参数 | 50 VU / 30s（读写比 1:500，刻意低并发） |
| 创建 QPS | **1,305** |
| 成功创建 | 39,172 条，**0 失败 0 5xx** |
| `idGenerator.syncLoadCount` 增量 | 1（预加载双 Buffer 全程跟得上，见 ADR-002） |
| `idGenerator.staleSegmentCount` | 0 |
| `t_id_segment.step` | 1000 |

> ⚠️ **这一轮跑通前修复了一个压测才暴露的真 bug——连接池自饿**：
> 原 `create()` 整体挂 `@Transactional`，而取号 `nextId()` 是 REQUIRES_NEW，
> 会挂起外层事务再从同一池里拿第二条连接 → 每请求同时占 2 连接，50 并发要 100 条、
> 池只有 20 → 集体 3s 超时 5xx（首测 5 QPS、145 个 5xx）。修法：事务只包落库一步，
> 风控/幂等/取号/生成短码移到事务外。详见 ADR-019。

## 故障降级演练

| 停掉的组件 | 跳转 QPS | P50 | 错误率 | 预期 | 实际是否符合 |
|---|---|---|---|---|---|
| （基线，统计关） | 16,117 | 8.6ms | 0% | — | — |
| RabbitMQ（**修复前**） | **155** | **1,277ms** | 0% | 完全不受影响 | ❌ **发现真 bug** |
| RabbitMQ（**熔断+异步化后**） | 与基线一致 | — | 0% | 完全不受影响 | ✅ 302=100% |
| **Redis**（降级逻辑上线后） | 3,819→**639** | 1.5ms | **0%** | QPS 下降但错误率 0% | ✅ **302=100%（42,276 次）** |
| **MySQL** | 2,223 | 7.8ms | 1.04% | 仍可用（数据不可变+缓存） | ✅ **98.96%（157,150 次 302）** |

> **★ MQ 宕机是本次压测抓到的最有价值的 bug**：broker 停机时 `convertAndSend` 在请求线程
> 阻塞到 connection-timeout（2s）才走降级，QPS 从 1.6 万崩到 155、P50 1.28s。
> "降级本地暂存"保住了数据（pending 增长、0 丢失），但**保不住延迟**。
> 修法：异步 publisher 线程组 + 时间型半开熔断（ADR-020/023）。
>
> **Redis 宕机**：降级路径 = L1 兜热点 + L1 miss 直查 DB（跳过 L2/BF/锁）。
> 错误率 0%，代价是 QPS 与 P99（Redisson 超时尾部 ~5.9s，可调 Redisson timeout 收敛）。
> 恢复 SOP：重启应用（Redisson 脚本缓存坑）→ `POST /admin/bloom/rebuild`。
>
> **MySQL 宕机**：98.96% 请求由 L1/L2 兜住，1.04% 是两层都没命中的冷码回源失败。
> 全量预热 L2 可趋近 100%——这正是"数据近乎不可变 → 缓存超长 TTL → DB 挂了热数据照常"
> 的架构优势。详见 ADR-015（含完整降级矩阵与恢复 SOP）。

**MQ 恢复后补投 drain 闭环验证**：停 MQ 期间缓冲的 100,000 条事件，broker 恢复后
全部补投落库，最终 `sum(daily pv) = sum(click_num) = 181,222`
（两口径完全一致，无丢失无重复）。**宕机→缓冲→恢复→补投全链路无损。**

## 统计链路开销归因（为什么"完整形态"比纯跳转慢）

统计采集（每请求 UUID + JSON 序列化 + 投递）跑在请求线程上，单独量化其代价：

| 形态 | QPS | 相对"统计关" | 说明 |
|---|---|---|---|
| 统计关（纯跳转，阶段③） | 16,117 | 100% | 跳转链路上限 |
| 统计开 + 只缓冲不投递（MQ 宕机+熔断） | 9,916 | -38% | UUID+JSON+入队代价 |
| 统计开 + 同步投递（关 confirms） | 3,165 | -80% | 每请求一次 MQ publish |
| 统计开 + 同步投递（开 confirms，默认） | ~1,185 | -93% | publisher-confirms 叠加开销 |
| **统计开 + 异步 publisher（Week 5 改造后）** | **12,831** | **-20%** | 请求线程只入队，后台 4 线程投递（ADR-023） |

> **结论（已落地）**：瓶颈不是 MQ 可用性，而是**"每请求同步 publish"这个动作本身**（叠加
> confirms 更甚，channel 缓存从 25 调到 256 反而恶化到 450 QPS/P99 6.5s）。
> Week 5 已改造为**异步批量投递**：请求线程只把事件放进有界内存队列（O(1)），
> 后台 publisher 线程组 drain + publish。完整形态 QPS **1,185 → 12,831（10.8x）**，
> 常规负载统计无损（300 次跳转 → pv 精确 300）。剩余 -20% 是 UUID+JSON 的固有代价。
> 详见 ADR-023。

## 火焰图发现（每一条都是无法伪造的面试素材）

本机未跑 async-profiler（Windows 环境），但压测过程实测抓到 8 个真实瓶颈，等价价值：

| # | 实测发现的问题 | 改了什么 | 效果 |
|---|---|---|---|
| 1 | **commons-pool2 缺失**：Lettuce 连接池配置被静默忽略，退化为单连接 | pom 加 commons-pool2 | 池化生效（ADR-022） |
| 2 | **utf8mb4_ai_ci 吞短码大小写**：唯一索引把 HNhTRj=HNHtrJ，灌 15 万行即碰撞 | short_uri 三列改 utf8mb4_bin | 100 万短码全唯一（ADR-021） |
| 3 | **创建链路连接池自饿**：@Transactional + REQUIRES_NEW 双占连接 | 事务边界收窄到只包落库 | 创建 5 QPS→1305 QPS，0 错误（ADR-019） |
| 4 | **MQ 宕机阻塞请求线程**：convertAndSend 同步阻塞 2s | 异步 publisher + 半开熔断 | MQ 宕机 155 QPS→不受影响（ADR-020/023） |
| 5 | **统计落库 upsert 列二义**：`pv=pv+new.pv` 在 MySQL 9.4 报 ambiguous | 表名限定 `t_link_stats_daily.pv` | 落库恢复，PV 对账 0% |
| 6 | **每请求同步 publish 是吞吐瓶颈**：统计开 QPS 掉到 1.2k | 异步批量投递（4 publisher 线程） | 1,185→12,831 QPS（10.8x，ADR-023） |
| 7 | **Redis 宕机无降级**：L2/BF/锁调用直接抛异常 → 500 | resolve 降级直查 DB + 告警限频 | 演练 302=100%，错误率 0（ADR-015） |
| 8 | **ShardingSphere 单表不自动路由**：t_id_segment TableNotFound | `!SINGLE` 规则 + `ds_0.*` 通配 | 号段/统计表正常（ADR-024） |

## 最终写进简历的句子（从上面的表里摘）

```
Zipf(α=1.0) 分布压测下，单机跳转 QPS 从 1.06 万(裸 MySQL) 提升至 1.61 万(+51%)，
P50 从 16.3ms 降至 8.6ms，L1 本地缓存命中率 63.7%（整体命中率 ~100%，稳态不落 DB）；

故障演练：MQ 宕机跳转不受影响（修复前 155 QPS 的阻塞 bug 由压测抓出并熔断修复），
Redis 宕机错误率 0%，MySQL 宕机热数据 98.96% 可用；
压测共定位并修复 8 个隐藏 bug（Lettuce 池化失效、短码 collation 碰撞、连接池自饿、

```

1. 标明分布和 α（Zipf α=1.0, seed=20260726）
2. 区分 L1 命中率（63.7%）与整体命中率（~100%）
3. 数字宁小勿夸 + 主动声明同机压测/后台噪声两个不诚实点
